# CRM Pulse Monitor

Локальный read-only дашборд для текущего состояния CRM Bitrix24 в GraphDB repository `bitrix24_v2_parallel`, который наполняет загрузчик v2 parallel. Сервер выполняет SPARQL `SELECT` к текущим RDF-графам, а браузер получает только готовый JSON. Архитектура монитора основана на [`rdf_store_monitor`](../Semantic_BI/rdf_store_monitor/README.md).

## Что показывает

- всего активных сделок с `b24:stageSemantic "P"`;
- активные сделки, созданные за последние 24 часа, 7 и 30 дней;
- график распределения активных сделок P по давности `lastActivityTime`: интервалы по 5 дней и отдельные группы для 30+ дней и отсутствующей даты; собственный фильтр показывает только категории с активными сделками;
- красные сделки: у сделок `P` нет записи активности, связанной с владельцем-сделкой (`OWNER_TYPE_ID=2`), за последние 7 дней;
- единый фильтр категории, который ограничивает KPI, список красных сделок, последние активности и таблицу сотрудников;
- вторая страница «Пульс лидов»: поступления за 1, 7 и 30 дней, среднее время до первой активности, список красных лидов и графики конверсии и активности;
- отдельная страница «Сотрудники»: топ-20 сотрудников по портфелю сделок P и график пульса сотрудников;
- раскрывающийся список красных сделок: название, ответственный, дата создания и `lastActivityTime` карточки Bitrix24;
- раскрывающийся список 20 последних активностей по сделкам: тема активности, семантический класс и название сделки, ответственный сотрудник;
- 20 сотрудников с наибольшим количеством назначенных сделок, у которых `stageSemantic = "P"`. При выбранной категории активности учитываются только записи, привязанные к сделкам этой категории (`OWNER_TYPE_ID=2`); в режиме «Все категории» сохраняется общий подсчёт активностей по ответственному.

Окна времени вычисляются в SPARQL от `NOW()` GraphDB. KPI, сотрудники и список красных сделок используют исходную семантику стадии `b24:stageSemantic "P"`; запросы не зависят от вывода OWL-класса. Для активности используется поле `CREATED` (`b24:createdAt`), для даты сделки — `DATE_CREATE`. Активности в таблице сотрудников считаются по `responsible` для всех владельцев CRM, а проверка бездействия сделок — только для активностей, где владелец является сделкой (`ownerTypeId=2`).

На странице лидов красными считаются лиды, созданные не менее двух часов назад, у которых первая активность появилась позже двух часов после создания или отсутствует; конвертированные лиды исключаются по наличию `deal.originLead` или `statusCode=CONVERTED`. В списке показываются 10 последних таких лидов, ФИО ответственного и источник. `sourceCode` разрешается в название из справочника, исходный код остаётся рядом. Графики «Пульс конвертации лида в сделку» и «Пульс активностей по лидам» показывают средние времена по дневным точкам за последние 90 дней, каждую точку — по скользящему 30-дневному окну. Конверсия считается до связанной сделки P в выбранной воронке `deal.categoryCode`. В выборках показаны размеры базы расчёта. История лидов и активностей ограничивается тем, что фактически загружено в RDF; текущий backfill лидов неполон. Категория сделки не является полем лида, поэтому фильтр категории на странице сделок не сужает статистику страницы лидов. На странице «Сотрудники» график пульса сравнивает среднее время реакции и конвертации; фильтр выбирает ответственного лида (`lead.assignedTo`), список отсортирован по фамилии и имени и ограничен сотрудниками с активностью за последние 30 дней. «Все сотрудники» агрегирует лиды этих сотрудников.

## Запуск локально

```bash
cd crm_pulse_monitor
test -f .env || cp .env.example .env
```

Проверьте `RDF_URL`, `GRAPHDB_REPOSITORY` и `GRAPH_PREFIX`. Для параллельного источника нужны `http://localhost:7200/`, `bitrix24_v2_parallel` и `urn:bitrix24:entity:garpix-bitrix24-ru-v2-parallel:`. Если GraphDB требует авторизацию, сохраните read-only учётные данные в локальном `.env`; секреты в браузер не передаются.

```bash
python server.py
```

Откройте <http://127.0.0.1:8082>. Сервер по умолчанию привязан только к loopback. Данные обновляются автоматически раз в минуту; ответы API кэшируются на 30 секунд. Список красных сделок загружается только при раскрытии.

Данные обновляются из текущей RDF-проекции, которую синхронизирует `bitrix24_v2_parallel`.

## Запуск в Docker Compose

Сервис подключается к внешней Docker-сети GraphDB (`graphdb_default` по умолчанию), читает настройки RDF из `.env` и публикует интерфейс только на loopback хоста.

```bash
cd crm_pulse_monitor
test -f .env || cp .env.example .env
docker compose up -d --build
```

Откройте <http://127.0.0.1:8082>. Если Docker-сеть GraphDB называется иначе, задайте её при запуске, например `RDF_DOCKER_NETWORK=my_graphdb_network docker compose up -d --build`. Адрес GraphDB по умолчанию — `http://graphdb:7200`; если имя сервиса или порт отличаются, задайте `RDF_URL_DOCKER`, например `RDF_URL_DOCKER=http://my-graphdb:7200`. Для другого порта на хосте задайте `CRM_PULSE_MONITOR_PORT`, например `CRM_PULSE_MONITOR_PORT=8092`.

Остановить монитор можно командой `docker compose down`. Контейнер работает с read-only корневой файловой системой и подключается к RDF-сети только для выполнения запросов.

## Структура

- `server.py` — HTTP API, конфигурация хранилища, read-only SPARQL client;
- `queries/` — отдельные запросы для KPI, сотрудников, категорий проектов, красного списка и последних активностей. Фильтр категории доступен отдельно для списка сотрудников и списка красных сделок.
- `static/` — интерфейс приложения.

Dashboard не пишет в RDF-хранилище. Метрики зависят от актуальности loader и доступности activity-событий в RDF.
