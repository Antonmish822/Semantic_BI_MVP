# CRM Pulse Monitor

Дашборд читает текущую RDF-проекцию Bitrix24 через GraphDB или Apache Jena Fuseki и отдаёт результаты через JSON API. Запросы CRM-данных только читают; отдельная административная страница онтологий умеет сохранять Turtle-файлы и публиковать онтологии в GraphDB.

Основные руководства: [конфигурация `.env`](docs/CONFIGURATION.md), [MCP и AI Agent](README_MCP.md), [управление онтологиями](ontologies/README.md). Шаблон конфигурации без секретов — [`.env.example`](.env.example).

## Страницы

### Пульс сделок

- Считает сделки в работе по `b24:stageSemantic "P"` и показывает новые сделки за 24 часа, 7 и 30 дней.
- Общий фильтр воронки ограничивает KPI, список красных сделок, последние активности по сделкам и график на вкладке «Сводки».
- «Красные сделки» — сделки P, созданные более 10 дней назад, у которых `lastActivityTime` и последние записи активности по `bindingDeal` и по владельцу-сделке (`ownerTypeId="2"`) не позже первых суток после создания. В списке показываются даты и сведения о последних найденных активностях по обоим типам связи; отсутствие записи означает, что она не найдена в RDF-проекции. Список загружается при раскрытии.
- Показывает 20 последних активностей по сделкам.
- На вкладке «Сводки» график распределяет активные сделки по давности `b24:lastActivityTime`: корзины по 5 дней, `30+ дней` и `Нет даты`.

### Пульс лидов

- На вкладке «Лиды» показывает поступления за 1, 7 и 30 дней, долю лидов с первой активностью в течение 2 часов среди созревшей 30-дневной когорты и дополнительное среднее время реакции.
- «Красные лиды» — лиды старше двух часов, без активности в первые два часа, без связанной сделки любой стадии и без `statusCode=CONVERTED`. В таблице выводятся 10 последних таких лидов, источник и ФИО ответственного.
- `sourceCode` разрешается в название из RDF-справочника источников; код показывается рядом.
- На вкладке «Сводки» график SLA показывает долю первых активностей за 2 часа, а график конверсии — среднее время до сделки P в выбранной воронке `deal.categoryCode`.
- Графики строятся по дневным точкам за последние 90 дней; каждая точка использует скользящее 30-дневное окно.

### Сотрудники

- После блока активных ситуаций доступен раскрывающийся список 10 последних активностей; его можно фильтровать по сотруднику и общей воронке.
- Таблица показывает 20 сотрудников с наибольшим портфелем активных сделок P среди тех, у кого были активности за последние 30 дней. Фильтр воронки ограничивает сделки и связанные с ними активности.
- «Пульс сотрудников» размещён на вкладке «Сводка».
- Сделки считаются по `assignedTo`. Активности считаются по `responsible`; в режиме «Все категории» учитываются активности по всем сущностям CRM, при выбранной категории — только активности, связанные со сделками этой категории.
- «Пульс сотрудников» показывает на одном графике среднее время реакции на лид и среднее время конвертации лида в сделку P. Фильтр выбирает сотрудника по ответственному лида (`lead.assignedTo`); в списке — сотрудники с активностью за последние 30 дней, отсортированные по фамилии и имени. «Все сотрудники» агрегирует данные этой группы.
- График пульса сотрудников использует дневные точки за последние 90 дней и скользящее 30-дневное окно.

## Расчёты и данные

Временные окна KPI и проверки бездействия сделок вычисляются в SPARQL от `NOW()` хранилища. Распределение сделок по `lastActivityTime`, показатели лидов и графики рассчитываются сервером от текущего времени в UTC. Для событий Activity используется `b24:createdAt` (поле Bitrix24 `CREATED`), для времени последней активности в карточке сделки — `b24:lastActivityTime`.

Первая активность лида — самая ранняя запись Activity, связанная через `b24:owner` при `ownerTypeId="1"`. Конверсия — самая ранняя связанная сделка со `stageSemantic="P"`; связь хранится в `b24:originLead`. Последняя активность сотрудника для фильтра «Пульс сотрудников» определяется по максимальному `activity.createdAt`, где сотрудник указан в `activity.responsible`.

Данные ограничены тем, что загружено в RDF-проекцию `bitrix24_v2_parallel`; история лидов и активностей неполная, если загрузчик не выполнил полный backfill. Справочники категорий и источников также должны быть загружены.

Интерфейс обновляет данные раз в минуту, ответы API кэшируются на 30 секунд. Красные сделки запрашиваются при раскрытии списка. В браузер не передаются учётные данные RDF-хранилища.



## Локальный запуск

Нужен Python 3.10 или новее и `uv` для установки зависимостей по `uv.lock`.

```bash
cp .env.example .env
```

Подробное описание переменных и режимов конфигурации находится в [справочнике конфигурации](docs/CONFIGURATION.md); [`.env.example`](.env.example) — полный шаблон без рабочих секретов. Для обычного dashboard настройте:

- `RDF_BACKEND=graphdb` или `RDF_BACKEND=fuseki`;
- для GraphDB задайте `RDF_URL` и `GRAPHDB_REPOSITORY`; для Fuseki задайте `RDF_URL` как URL dataset, например `http://127.0.0.1:3030/Persistent` (сервер добавит `/query`, если его нет в URL);
- задайте `GRAPH_PREFIX` для RDF-проекции. Пример адреса, repository и префикса показан в [`.env.example`](.env.example); подставьте значения вашего GraphDB стенда;
- если хранилище требует авторизацию, заполните `RDF_USERNAME` и `RDF_PASSWORD`;
- для Yandex ID укажите `AUTH_ENABLED=1`, `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` и (опционально) `AUTH_ALLOWED_DOMAINS`.
- задайте `ONTOLOGY_ADMIN_TOKEN`, чтобы разрешить административные операции с онтологиями и инструментами, включая публикацию запросов; `POLZA_API_KEY` нужен для помощника онтологий и AI-agent.

Установите зависимости и запустите сервисы в отдельных терминалах:

```bash
uv sync --locked
python -m mcp.mcp_server
```

```bash
python agent_service.py
```

```bash
python server.py
```

Откройте адрес из `DASHBOARD_HOST` и `DASHBOARD_PORT` (по примеру `.env.example`: <http://127.0.0.1:8085>).

## Запуск в Docker Compose

Compose поднимает Gateway, Auth, Analytics, Ontology, Agent, MCP и Redis для сессий Yandex ID. Только Gateway публикуется на хост (loopback, порт `8088` по умолчанию); внутренние сервисы соединены отдельными сетями. RDF-сервисы подключаются к существующей внешней Docker-сети GraphDB, по умолчанию `graphdb_default`, адрес GraphDB — `http://graphdb:7200`. Для сохранения TTL bind-mounted каталог `ontologies/` должен быть доступен дополнительной группе хоста. Настройка и команды находятся в [руководстве по онтологиям](ontologies/README.md).

```bash
cp .env.example .env
chmod g+rwx,g+s ontologies
CRM_MONITOR_GID="$(id -g)" docker compose up -d --build
```

Для конфигурации в `.env.ai-agent` задайте путь через `CRM_MONITOR_ENV_FILE`:

```bash
CRM_MONITOR_GID="$(id -g)" CRM_MONITOR_ENV_FILE=.env.ai-agent \
  docker compose --env-file .env.ai-agent up -d --build
```

`--env-file` нужен, чтобы Compose использовал значения из `.env.ai-agent` также для подстановки портов, URL GraphDB и Docker-сети. Подробности — в [справочнике конфигурации](docs/CONFIGURATION.md#как-приложение-читает-конфигурацию).

Если GraphDB опубликована на хосте, задайте её адрес из сети контейнера, например `RDF_URL_DOCKER=http://host.docker.internal:7200`.

Откройте <http://127.0.0.1:8088>. Если Docker-сеть GraphDB называется иначе, задайте `RDF_DOCKER_NETWORK`, например:

```bash
RDF_DOCKER_NETWORK=my_graphdb_network docker compose up -d --build
```

Если GraphDB недоступна по имени `graphdb`, задайте `RDF_URL_DOCKER`, например `RDF_URL_DOCKER=http://my-graphdb:7200`. Для отладки можно отдельно открыть loopback порты Agent и MCP, добавив `-f compose.debug.yaml` и задав `AGENT_SERVICE_PORT` / `MCP_SERVER_PORT`. Для Fuseki задайте `RDF_BACKEND=fuseki` и `RDF_URL_DOCKER` с URL dataset, доступным из Docker-сети.

Compose запускает контейнер с read-only корневой файловой системой и временным `/tmp`. Остановить сервис:

```bash
docker compose down
```

## AI Agent (Polza.ai + MCP)

HTTP API доступен по `POST /api/agent`, `/api/agent/profile`, `/api/agent/progress` и `/api/agent/query`; запросы проксируются дашбордом на выделенный сервис агента. История сообщений хранится в памяти процесса агента по `session_id`.

Режимы маршрутизации:

- `AGENT_MODE=proxy` — браузер вызывает `POST /api/agent` на дашборде, дашборд проксирует запросы в `AGENT_BASE_URL`.
- `AGENT_MODE=direct` — дашборд отключает агентский proxy (возвращает 404 на `/api/agent*`).

Описание всех переменных, их defaults, областей действия и различий между режимами приведено в [справочнике конфигурации](docs/CONFIGURATION.md); безопасный шаблон для настройки — [`.env.example`](.env.example). В частности, `AGENT_CONTEXT_MODE` принимает `baseline`, `p1` или `p2` и применяется после перезапуска `agent-service`. Отладчик SPARQL на `/tools/queries` вызывает только MCP; запуск в synthetic mode требует отдельного `AGENT_QUERY_DEBUG_ALLOW_SYNTHETIC=1` и изолированного synthetic repository. Этот флаг не требуется для разрешённой аналитической проекции. В запросе можно использовать `{{параметр}}`; `POST /api/agent/query` принимает шаблон в поле `query` и объект строковых значений `parameters`, экранирует значения как SPARQL string literals и передаёт результат штатной MCP-проверке. Формы определяют `xsd:dateTime`, `xsd:date`, `xsd:time`, boolean и числовые типы; `dateTime` из поля браузера преобразуется в UTC, а сервер проверяет лексический формат перед подстановкой. Успешно проверенный шаблон можно опубликовать на вкладку `/queries`; опубликованные запросы запускаются прямо из каталога, каталог хранится в Docker volume, а операции записи требуют `ONTOLOGY_ADMIN_TOKEN`. Если приложение находится за reverse proxy и для публикации появляется ошибка `Origin не соответствует адресу сервера`, задайте `PUBLIC_ORIGIN` равным внешнему origin, например `https://crm.example.org` (без пути); список forwarded-заголовков не используется.

Интерфейс чата доступен по адресу `/agent`.

Таблицы AI Agent и результаты опубликованных SPARQL-запросов используют общий браузерный экспорт в CSV и XLSX.

## Структура

- `server.py` — HTTP API, конфигурация GraphDB/Fuseki и расчёт показателей, плюс proxy на `/api/agent`;
- `agent_service.py` — HTTP API агента (FastAPI) и логика Polza.ai + MCP;
- `ontology_admin.py` — безопасное сохранение TTL и публикация через Graph Store Protocol;
- `ontology_assistant.py` — контекст и read-only инструменты помощника онтологий;
- `query_library.py` — атомарное файловое хранилище общего каталога опубликованных SPARQL-шаблонов;
- `ontologies/` — Turtle-аксиомы, доступные для редактирования на странице `/ontologies`;
- `queries/` — SPARQL-запросы для сделок, лидов, активностей, сотрудников и справочников;
- `static/index.html`, `static/leads.html`, `static/employees.html`, `static/agent.html`, `static/published_queries.html` — страницы интерфейса;
- `static/*.js` и `static/styles.css` — клиентская логика и стили;
- `docs/` — справочные материалы о доступных RDF-признаках и онтологии.

## Управление онтологиями

Страница `/ontologies` показывает список Turtle-файлов, статистику классов/признаков и связи по `rdfs:domain`/`rdfs:range`. Администратор вводит `ONTOLOGY_ADMIN_TOKEN`; браузер хранит его в `localStorage` до очистки поля. Проверка и сохранение TTL не меняют GraphDB. Публикация — отдельная операция: сервер вычисляет URI графа из slug, отправляет Graph Store Protocol PUT и сверяет опубликованный граф. Публикация поддерживается только для GraphDB. Кнопка «Удалить в карантин» сначала получает снимки SHA-256 файла, ревизионного архива и fingerprint графа, затем требует ввести slug. Перед удалением сервер сохраняет точный Turtle-снимок графа и повторно сверяет его fingerprint. TTL, ревизии и опубликованный граф хранятся в `ontologies/.quarantine` 30 дней по умолчанию. `ONTOLOGY_QUARANTINE_DAYS` задаёт срок от 1 до 3650 дней. Истёкшие записи очищаются фоновым процессом при запуске и далее раз в час. «Восстановить» возвращает все три объекта; если в GraphDB уже появился другой граф с тем же URI, он не перезаписывается и восстановление останавливается.

Помощник онтологий доступен при настроенном `POLZA_API_KEY`. Он предлагает проверяемые изменения; применить их в редакторе, сохранить файл и опубликовать граф администратор должен отдельно. В Polza.ai отправляются запрос, история текущего диалога и содержимое редактора; инструменты не возвращают CRM-литералы, имена, URI экземпляров или персональные данные.

## Аутентификация

Yandex ID включается переменной `AUTH_ENABLED=1`. Для использования задайте параметры OAuth в `.env`; callback должен совпадать с URI в настройках приложения Yandex. При необходимости ограничьте доступ через `AUTH_ALLOWED_DOMAINS`.
