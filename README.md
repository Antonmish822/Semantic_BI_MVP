# CRM Pulse Monitor

Read-only дашборд для текущей RDF-проекции Bitrix24. Сервер выполняет SPARQL `SELECT` к GraphDB или Apache Jena Fuseki, браузер получает результаты через JSON API. Дашборд не изменяет данные в CRM или RDF-хранилище.

## Страницы

### Пульс сделок

- Считает сделки в работе по `b24:stageSemantic "P"` и показывает новые сделки за 24 часа, 7 и 30 дней.
- Общий фильтр категории ограничивает KPI, список красных сделок и последние активности по сделкам.
- «Красные сделки» — сделки P без активности, где владелец является сделкой (`ownerTypeId="2"`), за последние 7 дней. Список загружается при раскрытии.
- Показывает 20 последних активностей по сделкам.
- График распределяет активные сделки по давности `b24:lastActivityTime`: корзины по 5 дней, `30+ дней` и `Нет даты`. У графика отдельный фильтр, в котором доступны только категории с активными сделками P.

### Пульс лидов

- Показывает поступления за 1, 7 и 30 дней, среднее время до первой активности и среднее время до связанной сделки P.
- «Красные лиды» — лиды старше двух часов, у которых первая активность появилась позже двух часов после создания или отсутствует. Лиды со связанной сделкой (`deal.originLead`) и лиды с `statusCode=CONVERTED` исключаются. В таблице выводятся 10 последних таких лидов, источник и ФИО ответственного.
- `sourceCode` разрешается в название из RDF-справочника источников; код показывается рядом.
- «Пульс конвертации лида в сделку» показывает среднее время до сделки P в выбранной воронке `deal.categoryCode`.
- «Пульс активностей по лидам» показывает среднее время от создания лида до первой активности.
- Оба графика строятся по дневным точкам за последние 90 дней; каждая точка рассчитывается по скользящему 30-дневному окну.

### Сотрудники

- Таблица показывает 20 сотрудников с наибольшим портфелем активных сделок P. Фильтр категории портфеля ограничивает сделки и связанные с ними активности выбранной категории.
- Сделки считаются по `assignedTo`. Активности считаются по `responsible`; в режиме «Все категории» учитываются активности по всем сущностям CRM, при выбранной категории — только активности, связанные со сделками этой категории.
- «Пульс сотрудников» показывает на одном графике среднее время реакции на лид и среднее время конвертации лида в сделку P. Фильтр выбирает сотрудника по ответственному лида (`lead.assignedTo`); в списке — сотрудники с активностью за последние 30 дней, отсортированные по фамилии и имени. «Все сотрудники» агрегирует данные этой группы.
- График пульса сотрудников использует дневные точки за последние 90 дней и скользящее 30-дневное окно.

## Расчёты и данные

Временные окна KPI и проверки бездействия сделок вычисляются в SPARQL от `NOW()` хранилища. Распределение сделок по `lastActivityTime`, показатели лидов и графики рассчитываются сервером от текущего времени в UTC. Для событий Activity используется `b24:createdAt` (поле Bitrix24 `CREATED`), для времени последней активности в карточке сделки — `b24:lastActivityTime`.

Первая активность лида — самая ранняя запись Activity, связанная через `b24:owner` при `ownerTypeId="1"`. Конверсия — самая ранняя связанная сделка со `stageSemantic="P"`; связь хранится в `b24:originLead`. Последняя активность сотрудника для фильтра «Пульс сотрудников» определяется по максимальному `activity.createdAt`, где сотрудник указан в `activity.responsible`.

Данные ограничены тем, что загружено в RDF-проекцию `bitrix24_v2_parallel`; история лидов и активностей неполная, если загрузчик не выполнил полный backfill. Справочники категорий и источников также должны быть загружены.

Интерфейс обновляет данные раз в минуту, ответы API кэшируются на 30 секунд. Красные сделки запрашиваются при раскрытии списка. В браузер не передаются учётные данные RDF-хранилища.



## Локальный запуск

Нужен Python 3.10 или новее; внешние Python-пакеты не требуются.

```bash
cp .env.example .env
```

Настройте `.env`:

- `RDF_BACKEND=graphdb` или `RDF_BACKEND=fuseki`;
- для GraphDB задайте `RDF_URL` и `GRAPHDB_REPOSITORY`; для Fuseki задайте `RDF_URL` как URL dataset, например `http://127.0.0.1:3030/Persistent` (сервер добавит `/query`, если его нет в URL);
- задайте `GRAPH_PREFIX` для RDF-проекции. Для параллельного источника используются GraphDB `http://127.0.0.1:7200/`, repository `bitrix24_v2_parallel` и префикс `urn:bitrix24:entity:garpix-bitrix24-ru-v2-parallel:`;
- если хранилище требует авторизацию, заполните `RDF_USERNAME` и `RDF_PASSWORD`.

Запустите сервер:

```bash
python server.py
```

Откройте <http://127.0.0.1:8082>. По умолчанию сервер привязан к `127.0.0.1:8082`; локальный адрес можно изменить через `DASHBOARD_HOST` и `DASHBOARD_PORT`.

## Запуск в Docker Compose

Compose подключает контейнер к существующей внешней Docker-сети GraphDB и публикует дашборд только на loopback хоста. По умолчанию сеть называется `graphdb_default`, адрес GraphDB — `http://graphdb:7200`, а порт хоста — `8088`.

```bash
cp .env.example .env
docker compose up -d --build
```

Откройте <http://127.0.0.1:8088>. Если Docker-сеть GraphDB называется иначе, задайте `RDF_DOCKER_NETWORK`, например:

```bash
RDF_DOCKER_NETWORK=my_graphdb_network docker compose up -d --build
```

Если GraphDB недоступна по имени `graphdb`, задайте `RDF_URL_DOCKER`, например `RDF_URL_DOCKER=http://my-graphdb:7200`. Для публикации на другом loopback-порту задайте `CRM_PULSE_MONITOR_PORT`, например `CRM_PULSE_MONITOR_PORT=8092`; контейнер по-прежнему слушает порт 8088. Для Fuseki задайте `RDF_BACKEND=fuseki` и `RDF_URL_DOCKER` с URL dataset, доступным из Docker-сети.

Compose запускает контейнер с read-only корневой файловой системой и временным `/tmp`. Остановить сервис:

```bash
docker compose down
```

## AI Agent (Polza.ai + MCP)

Минимальный HTTP API доступен по `POST /api/agent` и использует Polza.ai (OpenAI‑совместимый API) для генерации ответа и MCP-инструменты для выборок из RDF. История сообщений хранится в памяти процесса по `session_id`.

Переменные окружения:

- `POLZA_BASE_URL` — базовый URL API (по умолчанию `https://polza.ai/api/v1`);
- `POLZA_API_KEY` — ключ доступа к Polza.ai;
- `POLZA_MODEL` — модель Polza.ai (по умолчанию `polza-chat`);
- `POLZA_TIMEOUT` — таймаут запросов Polza.ai в секундах (по умолчанию `60`);
- `MCP_TIMEOUT` — таймаут запросов MCP в секундах (по умолчанию `30`);
- `AGENT_MAX_HISTORY` — максимальное число сообщений в истории (по умолчанию `12`);
- `AGENT_SYSTEM_PROMPT` — системный промпт агента (опционально).

Интерфейс чата доступен по адресу `/agent`.

## Структура

- `server.py` — HTTP API, конфигурация GraphDB/Fuseki и расчёт показателей, плюс endpoint `/api/agent`;
- `queries/` — SPARQL-запросы для сделок, лидов, активностей, сотрудников и справочников;
- `static/index.html`, `static/leads.html`, `static/employees.html`, `static/agent.html` — страницы интерфейса;
- `static/*.js` и `static/styles.css` — клиентская логика и стили;
- `docs/` — справочные материалы о доступных RDF-признаках и онтологии.
