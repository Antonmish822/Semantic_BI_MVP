# CRM Pulse Monitor

Локальный read-only дашборд для текущего состояния CRM Bitrix24 в GraphDB repository `bitrix24_v2_parallel`, который наполняет загрузчик v2 parallel. Сервер выполняет SPARQL `SELECT` к текущим RDF-графам, а браузер получает только готовый JSON. Архитектура монитора основана на [`rdf_store_monitor`](../Semantic_BI/rdf_store_monitor/README.md).

## Что показывает

- всего активных сделок с `b24:stageSemantic "P"`;
- активные сделки, созданные за последние 24 часа, 7 и 30 дней;
- красные сделки: у сделок `P` нет записи активности, связанной с владельцем-сделкой (`OWNER_TYPE_ID=2`), за последние 7 дней;
- раскрывающийся список красных сделок с фильтром по категории, названием, ответственным, датой создания и `lastActivityTime` карточки Bitrix24;
- отдельный раскрывающийся список 20 последних активностей по сделкам: тема активности, семантический класс и название сделки, ответственный сотрудник;
- 20 сотрудников с наибольшим количеством назначенных сделок, у которых `stageSemantic = "P"`; список можно ограничить категорией проекта. При выбранной категории активности учитываются только записи, привязанные к сделкам этой категории (`OWNER_TYPE_ID=2`); в режиме «Все проекты» сохраняется общий подсчёт активностей по ответственному.

Окна времени вычисляются в SPARQL от `NOW()` GraphDB. KPI, сотрудники и список красных сделок используют исходную семантику стадии `b24:stageSemantic "P"`; запросы не зависят от вывода OWL-класса. Для активности используется поле `CREATED` (`b24:createdAt`), для даты сделки — `DATE_CREATE`. Активности в таблице сотрудников считаются по `responsible` для всех владельцев CRM, а проверка бездействия сделок — только для активностей, где владелец является сделкой (`ownerTypeId=2`).

## Запуск локально

```bash
cd crm_pulse_monitor
test -f .env || cp .env.example .env
```

Проверьте `RDF_URL`, `GRAPHDB_REPOSITORY` и `GRAPH_PREFIX`. Для параллельного источника нужны `http://localhost:7200/`, `bitrix24_v2_parallel` и `urn:bitrix24:entity:garpix-bitrix24-ru-v2-parallel:`. Если GraphDB требует авторизацию, сохраните read-only учётные данные в локальном `.env`; секреты в браузер не передаются.

```bash
python server.py
```

Откройте <http://127.0.0.1:8082>. Сервер по умолчанию привязан только к loopback. Данные обновляются автоматически раз в минуту; ответы API кэшируются на 30 секунд. Список красных сделок загружается только при раскрытии.

Данные обновляются из текущей RDF-проекции, которую синхронизирует `bitrix24_v2_parallel`.

## Структура

- `server.py` — HTTP API, конфигурация хранилища, read-only SPARQL client;
- `queries/` — отдельные запросы для KPI, сотрудников, категорий проектов, красного списка и последних активностей. Фильтр категории доступен отдельно для списка сотрудников и списка красных сделок.
- `static/` — интерфейс приложения.

Dashboard не пишет в RDF-хранилище. Метрики зависят от актуальности loader и доступности activity-событий в RDF.
