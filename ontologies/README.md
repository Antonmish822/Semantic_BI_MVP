# Управление онтологиями и графами классификации

Файлы `*.ttl` в этой папке — единственный источник аксиом. Редактор доступен на `/ontologies`. Для каждого slug файла `<slug>.ttl` сервер вычисляет граф `urn:bitrix24:ontology:<slug>`; путь и URI графа браузер не задаёт. В Turtle должен быть ровно один субъект `owl:Ontology` с этим URI.

## Администрирование

Задайте длинный секрет `ONTOLOGY_ADMIN_TOKEN` в окружении сервера. Введите его на странице управления; браузер сохраняет токен в `localStorage` до очистки поля. Клиент передаёт UTF-8 токен в ASCII-safe Bearer-UTF8 заголовке, чтобы браузер принимал и Unicode секреты; сервер также совместим с прежними ASCII Bearer заголовками. Без токена запись отключена. Изменяющие запросы также проверяют `Origin`. Сервер ограничивает Turtle и запрос до 256 KiB. Публикация доступна только при `RDF_BACKEND=graphdb`; используются `RDF_URL`, `GRAPHDB_REPOSITORY`, `RDF_USERNAME`, `RDF_PASSWORD` и `RDF_TIMEOUT`.

Порядок работы: открыть файл или загрузить `.ttl`, указать slug, проверить Turtle, сохранить, затем отдельно нажать «Опубликовать сохранённую версию». Сохранение атомарно заменяет файл после проверки SHA-256 и не меняет RDF. Публикация всегда читает файл с диска, заменяет только вычисленный именованный граф и проверяет совпадение содержимого с учётом blank nodes. При таймауте PUT сервер не повторяет запись автоматически.

В Docker Compose `./ontologies` подключается как постоянный writable volume, при этом root filesystem остаётся read-only. Контейнер работает под UID 10001 и получает дополнительную группу хоста `CRM_MONITOR_GID`. На Linux дайте этой группе запись в каталог и включите наследование группы:

```bash
chmod g+rwx,g+s ontologies
CRM_MONITOR_GID="$(id -g)" CRM_MONITOR_ENV_FILE=.env.ai-agent docker compose up -d --build
```

Атомарно сохраняемые TTL получают режим `0664`; setgid-каталог сохраняет группу хоста, чтобы новые файлы оставались доступны для редактирования пользователем. Если группа каталога отличается от основной группы пользователя, назначьте каталог своей группе перед запуском.

## Существующие файлы и URI

| Файл | URI графа | Назначение |
|---|---|---|
| `lead-classification.ttl` | `urn:bitrix24:ontology:lead-classification` | Классификация лидов |
| `deal-classification.ttl` | `urn:bitrix24:ontology:deal-classification` | Классификация сделок |
| `activity-classification.ttl` | `urn:bitrix24:ontology:activity-classification` | Классификация активностей |
| `user-classification.ttl` | `urn:bitrix24:ontology:user-classification` | Классификация сотрудников |

Эти файлы и URI сохранены. RDF-данные сущностей остаются в собственных графах; правила онтологий хранятся отдельно.

## ИИ-помощник

Помощник доступен на странице `/ontologies` при настроенном `POLZA_API_KEY`. Ключ хранится только в окружении сервера. Модель задаётся `ONTOLOGY_AI_MODEL` (значение по умолчанию `openai/gpt-6-luna`), URL API — `ONTOLOGY_AI_BASE_URL`, таймаут — `ONTOLOGY_AI_TIMEOUT`, число вызовов чтения — `ONTOLOGY_AI_MAX_TOOL_CALLS`.

Внешнему провайдеру отправляются текст запроса, история текущей вкладки, текущий текст редактора и его SHA-256. При вызове соответствующих инструментов также передаются тексты сохранённых TTL и опубликованных графов онтологий, URI онтологий, имена предикатов из `docs/entity_properties.csv` и агрегированная статистика RDF. Инструменты не возвращают CRM-литералы, имена, URI экземпляров или персональные данные. Содержимое TTL, CSV и графов рассматривается как недоверенные данные, а не инструкции модели.

Предложение привязано к slug и SHA редактора/файла. Сервер проверяет структуру ответа и TTL, строит diff и показывает основания/предупреждения. Применение изменяет только редактор браузера. Сохранение и публикация остаются отдельными ручными действиями. Предварительные количества и пересечения по read-only запросам не доказывают полный вывод OWL 2 RL; для точной проверки нужен отдельный staging repository.
