# Дорожная карта перехода CRM Pulse Monitor на микросервисы

Связанный документ — [целевая архитектура](microservices_migration_architecture.md). Первый этап можно начинать с тестов действующего приложения. Дальше каждый этап добавляет один проверяемый результат, который сначала выпускается на стенд и переключается отдельно. Первым выносится Auth, затем Analytics, Ontology и каталог запросов. После выделения Gateway текущий Web UI можно по страницам заменить React-приложением.

## Среды и команды проверки

| Уровень | Что запускается | Данные и зависимости |
| --- | --- | --- |
| Unit | Python `unittest`, для React отдельные тесты TypeScript-клиента и компонентов. | Фиксированные часы, временные каталоги, синтетические fixtures. Ошибки транспорта задаются заглушками. |
| HTTP-контракты | Тот же набор вызовов против legacy и нового маршрута через Gateway. | Локальные HTTP-заглушки Yandex, Polza.ai, GraphDB/Fuseki и MCP по назначению теста. В сценариях межсервисного доступа запросы проходят по реальной HTTP-цепочке. |
| Compose | Сборка и запуск контейнеров, healthcheck, сетевые ограничения, перезапуск и откат маршрутов. | Отдельный тестовый проект со своими томами, сетью и тестовыми секретами. Redis для Auth настоящий. У стенда свои адреса зависимостей и отсутствует соединение с рабочей сетью RDF. |
| Браузер | Playwright через публичный URL Gateway. Chromium для каждого PR с UI-изменением, Firefox и WebKit перед выпуском нового UI. | Собранный статический UI или React, детерминированные ответы и отдельные сессии. Один тест проходит реальный HTTP-flow входа против заглушки Yandex. Остальные берут тестовую сессию из подготовки. |
| Staging | Репетиция входа с тестовым приложением Yandex, замеры и проверка Graph Store. | Изолированные GraphDB и Fuseki с синтетическим RDF. Запись и восстановление проверяются только в выделенном репозитории GraphDB. |

Команды, доступные в текущей ветке:

```bash
uv run --locked python -m unittest discover -s tests -v
uv run --locked python tests/bench_agent_context_modes.py
docker compose --env-file .env.example config --quiet
git ls-files 'static/*.js' | while IFS= read -r file; do node --check "$file" || exit; done
git diff --check
```

На этапе 0 добавить `tests/contracts/__init__.py`, чтобы полный `unittest discover` включал контракты, и отдельный `compose.migration-test.yaml`. Целевой вызов `docker compose -p semantic-bi-migration -f compose.migration-test.yaml run --rm checks` запускает контрактные и контейнерные проверки в изолированной сети. После добавления браузерного набора `npm --prefix web ci` устанавливает зависимости из lock-файла, `npm --prefix web run build` собирает React, `npm --prefix web run test:e2e` запускает Playwright против Gateway по адресу тестового стенда. Эти файлы и команды входят в этапы ниже. [Playwright в CI](https://playwright.dev/docs/ci) · [Сборка Vite](https://vite.dev/guide/#command-line-interface).

Для перехода использовать параметры `AUTH_SERVICE_URL`, `ANALYTICS_SERVICE_URL`, `ONTOLOGY_SERVICE_URL` и отдельное переключение каталога `QUERY_CATALOG_BACKEND=legacy|agent`. URL включает проксирование всей группы. При сбое переключение выполняется явно. В новом Gateway настроить маршрутизацию React через список `REACT_ROUTES`.

## Этап 0 Контракты и воспроизводимый стенд

**Работы.** Зафиксировать исходный commit и соответствие `метод + путь → сервис` по `server.py` и `static/*.js`. Добавить `tests/contracts/`, синтетические данные и HTTP-заглушки в `tests/fixtures/` и `tests/support/`. Зафиксировать в тестах ожидаемые статусы, JSON-поля и типы, выборочные тела по значениям, `Content-Type`, `Cache-Control`, `Location`, `Set-Cookie` и `X-Request-ID` там, где они часть контракта. Для сравнения заменять только динамические UUID и даты ответа. Порядок элементов, значения метрик и пользовательские ошибки проверять явно.

### Регрессионные проверки этапа 0

- **B0.1 Маршруты.** GET главной, всех страниц и алиасов, включая `/published-queries`, `/tools/ontology` и `/tools/queries`. Проверить наличие ресурсов и их MIME-типы. Для неизвестного URL и неподдерживаемого метода записать фактический ответ, включая разницу между JSON и страницей входа. Для HTML и API зафиксировать доступ с выключенным OAuth, без сессии и с действующей сессией.
- **B0.2 Данные.** Снять ответы для всех девяти аналитических маршрутов. Фикстура содержит пустые выборки, две категории, сотрудников и лидов с реакцией до, ровно в момент и после границы SLA. Сохранить `null`, нули, порядок строк и поведение при недоступности бэкенда. Отдельно сравнить наборы ситуаций `view-state` при локальном и контейнерном запуске. `rules/` сейчас отсутствует в Docker-образе, поэтому фиксируем исходные результаты каждого режима до отдельного изменения ресурсов.
- **B0.3 Текущие тесты.** Обновить `tests/test_ontology_assistant.py` под `suggest(payload, env, client_factory)` и `OntologyMCPTools`. Эмулировать три разрешённых инструмента MCP и текущие ответы модели. Сохранить проверки SHA, структуры ответа, таймаута и отсутствия записи. Тесты прямого CSV и удалённого `ReadTools` заменить проверками обязательного MCP-контекста, доступности fingerprint и отказа до модели. Существующую проверку наличия строк маршрутов в `server.py` заменить HTTP-проверкой через публичную точку входа до перемещения обработчиков.
- **B0.4 Базовый профиль.** Зафиксировать p50/p95 и долю ошибок для открытия страницы с параллельной загрузкой виджетов, холодного и тёплого кэша, входа, очереди лидов, чата и named query. Записать число SELECT, обращений к MCP и модели. Сравнивать на одном стенде, с одинаковыми fixtures, конкуренцией, числом прогонов и отдельно отмеченным прогревом. Для запросов с SPARQL `NOW()` размещать контрольные события вне границ окон или проверять точные границы на заглушках с фиксированным временем.

**Приёмка.** Полный `unittest` проходит в окружении из `uv.lock`. Один тестовый запуск воспроизводит публичные контракты без рабочего RDF, Yandex и коммерческих вызовов. По каждой строке маршрутизации есть сценарий и сохранённое ожидаемое поведение. Профиль содержит сырой результат и параметры запуска.

## Этап 1 Выделение общего RDF-кода и MCP

**Работы.** Вынести фабрику конфигурации, SELECT, пути к SPARQL-шаблонам, экранирование параметров и профилирование в `semantic_bi/common/` с отдельными модулями `rdf.py`, `query_templates.py`, `profiling.py`. Бизнес-методы клиента временно остаются в `server.py` и используют общий транспорт. Перевести `mcp/mcp_server.py`, `mcp/mcp_queries.py` и поздние импорты `mcp/safe_sparql.py` на новые модули. Формирование конфигурации MCP сохраняет различие между основным и аналитическим репозиториями, read-only учётными данными и пределами выполнения. Собрать самостоятельный target MCP.

### Проверки совместимости MCP

- **M1.1 Транспорт.** GraphDB и Fuseki формируют те же URL, заголовки, токены и SPARQL-результаты. Ошибка сети, таймаут, неверный JSON и отсутствующий шаблон воспроизводят прежний контракт. Запуск из другой рабочей директории находит файлы по абсолютным путям образа.
- **M1.2 Протокол.** Проверить `initialize`, `ping`, `tools/list`, `tools/call`, сохранение JSON-RPC `id`, разбор ошибок, поставляемый каталог именованных запросов и их параметры. Для ontology tools сравнить опубликованную схему, fingerprint, классы и агрегаты.
- **M1.3 Ограничения.** Сохранить проверки существующего `tests/test_safe_sparql.py` для аутентификации, разделения областей данных, лимитов времени и размера, подавления малых групп, отказа до обращения к RDF и отсутствия CRM-значений в результатах модели и журналах. Проверить оба поддерживаемых режима MCP и выключенный feature flag.
- **M1.4 Образ.** В контейнере MCP отсутствует `server.py`, все обязательные ресурсы на месте, процесс запускается от непривилегированного пользователя. Проводятся smoke-вызов от Agent и проба действующего внешнего MCP-клиента через разрешённый loopback endpoint.

**Приёмка и откат.** Unit, HTTP-контракты и проверка образа проходят. Временные импорты обратной совместимости находятся в legacy-процессе. Для возврата достаточно предыдущего образа MCP и тех же настроек.

## Этап 2 Auth и сессии Yandex ID

**Работы.** Добавить `services/auth/app.py`, модули Yandex, сессий и хранилища; использовать FastAPI и приватный Redis с TTL. Контракт `GET /internal/session` принимает сессионную cookie и отдельный межсервисный секрет Gateway. Auth отвечает `200` с минимальным ID пользователя, `401` при недействительной сессии или `503` при отказе хранилища. Через адаптер в `server.py` одновременно переключать `/auth/*` и проверку доступа. Сохранить внешний callback, запретить передачу OAuth-секрета другим сервисам и фильтровать заголовки идентичности на входе.

### Unit и HTTP-проверки Auth

- **A2.1 Вход.** Успешный callback выпускает новую cookie и возвращает на проверенный локальный URL, включая параметры. Проверить отсутствующий, подменённый, истёкший и повторно использованный `state`, привязку к инициировавшему браузеру и две параллельные попытки погасить state. Каждая недействительная попытка завершается до запроса токена. Для внешнего пути возврата ожидается безопасный локальный маршрут.
- **A2.2 Провайдер.** Разрешённый и запрещённый домен, пустой или неполный профиль, отказ пользователя, ошибка или таймаут token/profile, неподходящий внешний callback в конфигурации. Ошибка входа не создаёт сессию. При отключённом OAuth проверить только явно заданный локальный режим.
- **A2.3 Сессии.** Проверить `HttpOnly`, `Secure` на HTTPS, `SameSite`, путь cookie и её очистку при выходе. После logout и по TTL прежний идентификатор отклоняется. Сессия доступна через другой экземпляр Auth и после перезапуска процесса при сохранённом Redis. При отказе Auth или Redis закрытые маршруты возвращают `503`, а публичная обработка продолжает работать. Недоступность Yandex не мешает проверке ранее созданных сессий.
- **A2.4 Gateway.** Проверить `/auth/status` для гостя и пользователя, сохранение браузерного редиректа на переходном этапе, недоступность `/internal/session` снаружи, отказ при отсутствующем или неверном межсервисном секрете и отсутствие доверия к присланному клиентом ID. Проверить отсутствие в логах cookie, кода OAuth и токенов, в том числе в callback query string.

### Стендовая приёмка Auth

Пройти реальный вход с тестовым приложением Yandex по HTTPS, возврат на исходный URL, выход и повторный вход. Переключение и откат включают одновременно все `/auth/*` и проверку сессии, поскольку старые сессии находятся в памяти legacy-процесса. Оба сценария должны предсказуемо запрашивать повторный вход и сохранять внешний callback.

## Этап 3 Analytics

**Работы.** Добавить `services/analytics/app.py`, перенести метрики, проверку фильтров, справочники, кэш и `view-state`. HTTP-обработчики с синхронным I/O запускать вне event loop. Сохранить поддержку GraphDB/Fuseki и текущий вид ошибок в UI. Переключать все девять маршрутов одним блоком. Кэш, бизнес-формулы и ожидаемые ресурсы переносить без изменения поведения. Исправление набора правил в образе и оптимизация кэша идут отдельными изменениями после сравнения.

### Проверки Analytics

- **D3.1 Метрики.** Сравнить legacy и новый сервис на одинаковых fixtures. Проверить сделки по проектам, красные сделки и лиды, активности по сотруднику, категории, тренды реакции и конверсии, SLA и динамическое отображение блоков. Покрыть неизвестный фильтр, пустую выдачу, границы временных окон, повторные URI, сортировку и nullable поля.
- **D3.2 Кэш и сбои.** Первое чтение, попадание, истечение TTL, независимость фильтров, fallback включён и выключен, отказ при пустом кэше, восстановление после ошибки, параллельные запросы. Проверить число вызванных SELECT. Контракт `available: false` сравнивать отдельно от транспортного отказа Analytics.
- **D3.3 Сборка и нагрузка.** Отдельные smoke-прогоны на GraphDB и Fuseki. В контейнере используемые шаблоны, правила и профиль схемы доступны. Провести нагрузочный профиль при том же параллелизме и убедиться, что аналитика не делает дополнительных SELECT на тот же пользовательский сценарий.

**Приёмка и откат.** Совпали контракты и значения, все UI-зависимости обслуживаются одним backend. Откат возвращает весь блок Analytics к legacy без смены Auth и UI.

## Этап 4 Ontology и каталог запросов

**Работы.** Добавить `services/ontology/app.py` и забрать управление TTL, ревизиями, карантином, публикацией, статистикой и помощником. Graph Store остаётся внутри Ontology. Помощник получает опубликованную схему и агрегаты через разрешённые ontology MCP tools. Вместе с томом перенести задачу очистки просроченного карантина. Независимым изменением перенести `query_library.py`, `/api/published-queries*` и volume `published_queries` в Agent. У обоих томов при переключении один активный пишущий процесс.

### Проверки Ontology

- **O4.1 Файлы и REST.** Список, чтение, валидация, создание, изменение, статусы и история публикаций. Проверить некорректный slug и TTL, предел тела, отсутствующий и устаревший SHA, два одновременных сохранения, ошибку прав на том и перезапуск после сохранения. Сохранение меняет только TTL и связанные локальные данные. Зафиксировать действующие коды ошибок и совместимость ASCII/UTF-8 admin bearer и `PUBLIC_ORIGIN`.
- **O4.2 Graph Store.** Подтверждённый PUT → GET, отсутствие графа, несовпадение графов, сетевой отказ до применения и потеря ответа после применения. В неопределённом состоянии сначала сверить результат. Проверить один PUT, корректный URI, RDF-эквивалентность и неизменность соседних графов. Проверить откат к последней отличающейся подтверждённой ревизии, конфликт SHA и поведение Fuseki.
- **O4.3 Карантин.** Предпросмотр без изменения данных, конфликт любого fingerprint, снимок TTL/ревизий/графа, потеря ответа после DELETE, повторный просмотр, восстановление исходного состояния, отказ при несовместимом существующем графе или файле. Проверить срок очистки и сохранение записей аудита. На стенде воспроизвести обрыв между Graph Store и файловым действием и подтвердить восстановимость из снимка.
- **O4.4 Помощник.** Проверить `config`, `version`, `suggest`, версии редактора и файла, актуальный fingerprint графа, ошибки MCP и Polza.ai, ответ с невалидным TTL. Модель не вызывается при устаревшем SHA или недоступном обязательном контексте. Успешное предложение не меняет файл или GraphDB.

### Проверки каталога запросов

- **Q4.1 Каталог.** GET, создание, список, запуск, удаление и отказ без административного заголовка или при чужом Origin. Ошибка формата, дубликат, отсутствующий ID и одновременное изменение покрываются HTTP-тестами.
- **Q4.2 Запуск.** Через `POST /api/agent/query` проверить подстановку параметров, текущие поддерживаемые типы, пустую выдачу, ошибку MCP и режимы policy. В каталоге хранятся шаблоны, значения параметров и образцы результата в сохраняемую запись не входят.
- **Q4.3 Том.** Пересоздание Agent сохраняет записи. При откате старому обработчику передаётся актуальный том. Работа чата и профиля проверяется с остановленным сервисом Ontology.

**Приёмка и откат.** Для каждого тома проведена репетиция остановки приёма записей, завершения активных операций, резервной копии и передачи владельцу. Проверки записи RDF выполнены только в выделенном staging repository. При откате остановить нового писателя, вернуть актуальные данные и до возобновления записи сверить файл, журнал, ревизии, карантин и GraphDB. Один пользовательский запрос вызывает ровно одну попытку записи на стороне Gateway.

## Этап 5 Gateway и отдельный Web UI

**Работы.** Добавить `services/gateway/app.py` с явной таблицей HTTP-маршрутов. Собрать статический Web UI из текущего `static/`. Разделить внутренние Compose-сети, секреты и образы. Через внешний порт оставить только Gateway, а доступ MCP по loopback сохранить отдельным профилем. У каждого сервиса настроить liveness/readiness, сквозной `X-Request-ID` и ограниченные таймауты. Readiness проверяет только критичные для данного сервиса зависимости, чтобы сбой одного домена не скрывал весь Gateway. В защищённом режиме Agent привязывает историю и прогресс к проверенному ID пользователя из Gateway, сохраняя публичные `session_id` и `request_id`.

### Контейнерные проверки Gateway

- **G5.1 Маршрутизация.** Методы, query string, cookie, редиректы, критичные заголовки, входные лимиты, ошибки JSON и статусов. Недействительные маршруты и методы возвращают ожидаемые ответы. Запросы `/api/*`, `/auth/*` и `/internal/*` не попадают в HTML fallback.
- **G5.2 Отказы и прогресс.** Остановить по очереди Auth, Analytics, Ontology, Agent и MCP. Проверить готовность и ответы, заданные для каждого отказа. При остановке аналитики CSS, страницы с действующей сессией и чат доступны. При отказе MCP чат и помощник получают собственные ошибки. Долгие и изменяющие вызовы не повторяются прозрачным прокси. Чат проверяется одновременно с опросом прогресса, включая задержанный ответ модели и передачу `request_id`. Если синхронный вызов модели блокирует опрос, вынести его в ограниченный пул. HTTP-тест с двумя пользователями проверяет изоляцию истории и прогресса.
- **G5.3 Права и сборки.** У Gateway, Auth, Web UI и Agent нет сетевого маршрута к RDF и его секретов. Analytics и MCP имеют только чтение. Запись Graph Store разрешена только Ontology. Том онтологий доступен на запись только этому сервису. Логи и отчёты прогонов показывают статусы и длительность без payload, персональных данных и секретов.

**Приёмка и откат.** Одна сборка Compose проходит HTTP и браузерный smoke с текущим UI. Перезапуск каждого контейнера воспроизводим. Откат внешнего маршрута проверяется со свежими сессиями и актуальными томами. Переходные обработчики удаляются отдельным изменением после подтверждения рабочего отката и периода стабильной работы.

## Выпуск и критерии остановки

1. На каждый PR сохранять результат полного `unittest`, актуальный набор контрактов и результаты сборки затронутых сервисов. До первого внешнего переключения добавить полный Compose smoke и браузерные сценарии на собранном образе. Новый ожидаемый исход сначала фиксируется тестом. Старое поведение сначала характеризуется проходящим тестом, который должен пройти и после переноса.
2. Перед выпуском повторить профиль B0.4 с одинаковыми данными и нагрузкой. Как стартовый порог для staging принять p95 не выше базового более чем на `max(10%, 50 мс)` по каждому ключевому сценарию, долю ошибок не выше базы и то же число SELECT/MCP/модельных вызовов там, где функциональность прежняя. Оценивать стенд серией одинаковых прогонов, а не единичным CI-замером. Отдельно показать вклад проверки сессий. Уточнить порог по фактической базе до переключения.
3. Перед каждой группой маршрутов сохранить предыдущий образ и конфигурацию маршрутизации, проверить откат на staging. Для Auth подготовить повторный вход. Для Ontology и каталога проверить состояние обоих томов перед передачей записи. Повторить smoke после переключения и после отката.
4. Откатывать группу при расхождении контрактов, ошибке контроля доступа, потере данных, нарушении целостности графов или повторяемом выходе за порог. Фиксировать commit, версии образов, команду прогона, ожидаемый и фактический результат и причину отката. Результаты без секретов прикладывать к PR или отчёту выпуска.

## Журнал реализации

### Этапы 0–1: контракты, общий RDF-код и MCP

- Добавлены HTTP-проверки legacy страниц, алиасов, MIME-типов ресурсов, 404 и двух режимов гостевой сессии.
- RDF-конфигурация и SELECT-транспорт вынесены в `common/rdf_transport.py`; загрузка SPARQL-шаблонов и экранирование вынесены в `common/query_templates.py`. Доменные методы `RDFStoreClient` используют общий транспорт через совместимый подкласс.
- Загрузка окружения и профильная телеметрия доступны в `common/runtime.py`. MCP, named-query renderer и safe-SPARQL больше не импортируют `server.py`.
- Dockerfile получил цели `dashboard`, `agent` и `mcp`. Compose явно выбирает каждую цель. MCP-образ содержит только нужные библиотеки и ресурсы, включая named-query каталог и RDF-справочники; `server.py` в нём отсутствует. В dashboard-образ добавлены правила, применяемые `view-state`.
- Проверки прошли: Compose config, Python compile/AST, JavaScript syntax, 18 тестов для HTTP-контрактов, RDF-транспорта и существующих правил управления онтологиями. Docker-образ MCP собран, импорты MCP проверены внутри контейнера без `server.py`.
- Тесты помощника обновлены к MCP HTTP-контракту: прямой GraphDB доступ и удалённый `ReadTools` больше не фигурируют; проверяются ошибки MCP, версии редактора/файла, безопасная валидация и отсутствие записи.
- Текущая команда полного набора в контейнере: `docker run --rm --tmpfs /tmp -v "$PWD:/app:ro" -w /app -e AGENT_PROFILE_LOG_DIR=/tmp/profile semantic_bi_mvp-crm-pulse-monitor python -m unittest discover -s tests -v`. Последний прогон: 68 тестов прошли. Профильные проверки используют `/tmp/profile`, потому что корневая файловая система контейнера read-only.

### Этап 2: Auth и сессии Yandex ID

- Добавлен `services/auth/app.py`: OAuth callback Yandex, Redis TTL для одноразового state и сессий, проверка email-домена, безопасный локальный `next`, browser-bound state cookie, logout с отзывом сессии.
- Добавлен внутренний `GET /internal/session`: принимает сессионную cookie и межсервисный `X-Gateway-Secret`, возвращает только `user_id`; при отказе Redis отвечает `503`. `/auth/*` и проверка доступа переключаются вместе через `AUTH_SERVICE_URL` в Gateway-адаптере `server.py`.
- Compose получил Auth и Redis services, отдельную внутреннюю сеть, persistent AOF volume и отдельный egress для запросов к Yandex. OAuth и ненужные Auth секреты очищаются в других контейнерах; Auth не присоединён к RDF-сети. Uvicorn access log выключен, чтобы callback query не попадал в журналы.
- Docker targets всех сервисов собираются, `docker compose config --quiet` проходит. Auth, Gateway и assistant HTTP/unit тесты проходят; общий набор: 60/60.
- В изолированной временной Docker-сети два Auth-контейнера прочитали одну синтетическую Redis-сессию; она сохранилась после перезапуска первого Auth. Контейнеры и сеть удалены после smoke.
- На staging остаётся реальная проверка тестового приложения Yandex по HTTPS, production `AUTH_PUBLIC_ORIGIN`, отказов между Auth и Gateway и security/logging review. До неё OAuth не считается принятым на стенде.

### Этап 3: Analytics и `view-state`

- RDF-клиент, запросы, формулы метрик, кэш, fallback, профиль онтологии и правила `view-state` перенесены в `services/analytics/domain.py`; `server.py` сохраняет импорт legacy функций и обрабатывает старые маршруты при отключённом сервисном URL.
- Добавлен FastAPI сервис `services/analytics/app.py` с девятью прежними API путями. Синхронные обработчики FastAPI выполняет в worker pool; контракты фильтров и ошибок сохранены. `ANALYTICS_SERVICE_URL` переключает весь блок в Gateway одним набором маршрутов.
- Docker target Analytics включает только runtime-код аналитики, общие RDF/query модули, `queries/`, `docs/` и `rules/`; контейнер не публикует порт наружу и подключён к внутренней сети Gateway и сети RDF. Analytics не получает OAuth, Polza.ai или admin секреты.

### Этап 4: Ontology и каталог запросов

- Управление TTL, ревизиями, публикацией, карантином, статистикой классов и предложениями помощника вынесено в `services/ontology`; каталог шаблонов и его `published_queries` volume принадлежат Agent. TTL bind mount используется только Ontology. Очистка просроченного карантина работает в lifecycle процесса Ontology.
- В `server.py` сохранены совместимые локальные обработчики и proxy на сервисы через `ONTOLOGY_SERVICE_URL` и `AGENT_BASE_URL`; при рабочем Compose маршруты идут через Gateway. Redis не используется каталогом или Ontology: он нужен только Auth для state и сессий Yandex ID.

Веб-форма отправляет строковые параметры согласно существующему API renderer; он экранирует каждое значение как SPARQL string literal, datatype conversion отдельно не заявляется.

### Этап 5: Gateway и отдельный Web UI

- `services/gateway/app.py` обслуживает публичные URL из явной таблицы, направляет Auth, Analytics, Ontology и Agent по внутренним сетям и добавляет `X-Request-ID`. Есть health/readiness, ограниченный timeout и лимит тела проксируемого запроса `GATEWAY_MAX_BODY_BYTES` (по умолчанию 16 MiB). `/internal/session` не проксируется.
- Только Gateway публикуется в основном Compose. Loopback-порты Agent и MCP доступны отдельно через `compose.debug.yaml`. Добавлены private сети, контейнерные healthchecks и очистка OAuth/admin секретов из нецелевых сервисов. Gateway image smoke подтвердил React page/assets, переключение на legacy и отсутствие `server.py` внутри образа.
- `docker compose config --quiet` и конфигурация с debug override прошли; `docker compose build` собрал шесть образов. Первичная сборка поймала отсутствие `static/styles.css` в Node stage; файл добавлен в stage, после чего сборка React и всех Docker images прошла. `.dockerignore` исключает npm и Playwright артефакты.
