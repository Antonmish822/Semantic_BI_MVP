# План замены lead_lifecycle на странице «Лиды»

## 1. Цель и границы

Ускорить холодный `GET /api/lead-pulse` и дать странице два рабочих показателя: как часто лид получает первую зафиксированную активность в течение двух часов и какие лиды требуют внимания. Сохранить счётчики новых лидов, среднее время реакции и график конверсии по воронкам. Список красных лидов по-прежнему охватывает всю историю.

Страница переходит на специализированные чтения. Именованный MCP-запрос `lead_lifecycle` сохраняет имя, параметры, поля, типы и порядок выдачи. Для новой аналитики добавить отдельный именованный запрос с явно выбранным контрактом. Ускорение старого MCP-запроса можно проверять отдельным экспериментом, без зависимости от миграции страницы.

Источники: [предыдущий план](lead_lifecycle_optimization.md), [отчёт с исправлением](../logs/lead-lifecycle-optimization-report.md), [исторический бенчмарк](../logs/graphdb-benchmark-4.json). Историческая медиана `lead_lifecycle` — 9,13 с, `lead_employee_pulse` — 78 мс при наличии таких же двух MIN. Это повод проверить форму соединений, но вклад конкретных операторов не измерен. Прошлые B и C запускали исходный SPARQL из-за подстановки префикса до текстовой замены. D менял порядок, выигрыш не показан. В длинном исходном прогоне выборка изменилась с 192 до 193 строк.

## 2. Определения показателей и договорённости

Один запрос страницы использует один `as_of` в UTC. Каждая точка тренда считается на тот же UTC-момент соответствующего дня, от `as_of − 89 дней` до `as_of` включительно. На точку берутся лиды из [точка − 30 дней, точка]. Значит, полная выборка для тренда начинается с `as_of − 119 дней`. Все сравнения выполняются по моментам времени, отображение времени на странице остаётся локализованным.

| Показатель | Правило |
|---|---|
| Новые лиды | Один лид на URI в каждом из скользящих окон 1, 7 и 30 дней. Обе границы включены. |
| SLA реакции | Знаменатель: лиды в 30-дневной когорте, у которых к моменту расчёта прошли два часа. Числитель: лиды из знаменателя с активностью в интервале [создание, создание + 2 часа]. Активность ровно через два часа засчитывается. Отсутствие активности у созревшего лида считается нарушением. При пустой выборке доля равна null. |
| Среднее время реакции | Дополнительная метрика. Среднее до первой валидной активности среди лидов в 30-дневной когорте с активностью к моменту расчёта. Включает лиды моложе двух часов, если они уже получили активность. Показывать размер выборки. Сохранить исторический ряд среднего для действующих правил страницы. |
| Красные лиды | По всей истории. Лид создан не менее двух часов назад, его статус при сравнении без учёта регистра отличен от CONVERTED или отсутствует, у него нет ни одной связанной сделки любой стадии и нет активности в первые два часа. Сортировка по моменту создания по убыванию, затем по URI по возрастанию. Первые 10 уникальных лидов. |
| Конверсия | Сохранить уже имеющийся график по воронкам и его источник. Карточку исторического среднего времени до первой связанной сделки стадии P заменить карточкой SLA. |

Активность относится к лиду через `owner` и `ownerTypeId "1"` в именованном графе активности. Для новой аналитики учитывать только распознанные метки времени от момента создания лида. В частности, запись активности раньше создания не закрывает SLA. В старом коде такая запись могла повлиять на список красных лидов из-за глобального MIN. Отразить это, переход от кратности строк к уникальным лидам и новый порядок при равных датах как осознанные изменения. Не смешивать знаменатель SLA со списком красных лидов: отсутствие сделки и статус применяются только к очереди.

Если в данных есть несколько дат создания одного URI, выбрать самую раннюю валидную дату. Для неоднозначного статуса исключать из очереди лид с любым статусом CONVERTED. Обогащение справочниками должно сохранять один результат на лид. При пропущенном или неизвестном ключе показывать текущие значения по умолчанию. При нескольких ключах или совпадениях выбрать одно значение по документированному устойчивому правилу, например лексикографически минимальный ключ и затем минимальную непустую подпись. Покрыть это синтетическими данными.

## 3. Реализация по этапам

### 3.1 Диагностика и прототип SPARQL

1. Проверить инструкции проекта, рабочее дерево и все вызовы `/api/lead-pulse`, `lead_pulse()` и `lead_lifecycle`. Согласовать форму ответа с фактическими потребителями. Сохранить изменения пользователя.
2. Снять свежую базу по процедуре ниже. План `onto:explain` и профиль `onto:measure` запускать отдельно от измерений задержки. Сохранить кардинальности и времена доступных шагов без значений CRM.
3. Реализовать отдельный шаблон узкой выборки для реакции и счётчиков. Получать URI, время создания и первую валидную активность только для когорты 119 дней. Ограничение по лидам должно действовать внутри соединения с активностями и агрегации. Для диагностики сравнить вариант с группировкой по ограниченной когорте и вариант с двумя чтениями: список лидов, затем MIN для URI из списка через пакетный VALUES. У второго варианта считать все HTTP-вызовы и объём ответа.
4. Реализовать отдельный шаблон очереди. Проверить отсутствие любой сделки и наличие активности в первые два часа через антисоединения или эквивалентные маркеры, без глобального MIN активности. Начальный набор включает всю историю. Если глобальное антисоединение дорого, проверить отбор кандидатами от новых к старым с устойчивым курсором по паре (время создания, URI). Прекращать после 10 подходящих лидов либо исчерпания истории. Один произвольный LIMIT до проверки условий может потерять лидов и не годится.
5. Применить LIMIT 10 после проверки условий и упорядочивания уникальных лидов. Получить заголовки и справочники для финальных URI. При разделении на несколько SELECT сохранять порядок из списка URI, учитывая типы RDF и безопасную сериализацию. Использовать тот же префикс именованных графов и условия из нужных сущностей.
6. Снять 5–10 замеров на каждый действительный вариант. Хранить варианты отдельными файлами или изменять сырой шаблон до подстановки префикса. Скрипт должен завершаться ошибкой, если ожидаемая замена не произошла, и проверять разные хеши итогового SPARQL. Для старого MCP при наличии времени повторить корректный B: максимум один маркер на лид, флаг любой сделки и дата MIN только для P. C повторять раздельно для каждого справочника при диагностике плана. Любая правка старого запроса требует отдельного доказательства эквивалентности и выигрыша.

### 3.2 Сервер, страница и MCP

1. В `server.py` собрать ответ из выбранных узких чтений. Общий `as_of` передавать каждому шаблону и вычислениям. Рассчитывать 90 точек в Python для первого кандидата. Сохранить существующий путь кеширования и обработки ошибок, проверить промах, попадание и ошибку одного из чтений. Публиковать результат в кеш после успешной сборки всех блоков.
2. Сохранить поля верхнего уровня `available`, `backend`, `as_of`, `summary`, `response_trend` и `red_leads`. В summary добавить `sla_within_2h_ratio` (от 0 до 1 или null), `sla_within_2h_count` и `sla_eligible_count`. В каждую точку тренда добавить те же поля. Сохранить поля среднего и выборки среднего, даты тренда и поля строк очереди. Карточка конверсии перестаёт использовать `average_conversion_days` и `conversion_sample_size`. Удалять эти поля из API только после аудита потребителей и согласованного перехода. Если есть внешняя зависимость, предложить отдельную версию ответа для старого контракта и замерять путь новой страницы отдельно.
3. В `static/leads.html` и `static/leads.js` показать процент SLA, значения числителя и знаменателя и пояснение про первую активность. Для графика SLA использовать шкалу 0–100%, показывать выборку в подсказке и разрывы на пустых точках. Оставить среднее в карточке как дополнительную метрику и существующий график конверсии. Сохранить идентификаторы блоков для правил вида. В `build_leads_metrics()` проверить, что действующие правила продолжают получать среднее и его тренд. Пересмотр порогов правил SLA вынести за рамки этой задачи.
4. В `mcp/mcp_queries.py` добавить именованный `lead_response_sla` с компактной агрегированной выборкой: одна строка с числителем, знаменателем и долей за 30 дней на обязательное время `as_of`. Переиспользовать определение когорты и условий SLA из пути страницы. Проверять параметр как UTC дату и время до подстановки штатным экранированием. Проверить пустую выборку, типы ответа, каталог MCP, вызов с валидным параметром и ошибки при отсутствующем или неверном параметре. Документировать запрос в `README_MCP.md`. При полном прогоне каталога передать `as_of` через файл параметров.

## 4. Проверки

Сначала выполнить проверки на синтетическом RDF и фиксированном UTC-времени. Проверить начало и конец окон 1/7/30/119 дней, момент ровно два часа, активность на секунду раньше и позже, отсутствие активности, события до создания и после момента расчёта, несколько активностей, посторонний тип владельца, любые стадии сделки, статус CONVERTED и его отсутствие. Добавить лид старше 119 дней, который попадает в очередь, и несколько лидов с одинаковой датой на границе десятки. Проверить пустую выборку, пропущенные и многозначные поля и справочники, разные часовые смещения одной даты, отсутствие дублей от соединений.

Сравнить новые счётчики, среднее, упорядоченную очередь и все 90 точек с исходным ответом. Объяснить каждое обнаруженное расхождение по правилам раздела 2. SLA проверить независимым ручным расчётом на фикстуре, включая пустой знаменатель. Проверить страницу, API, правила вида и старый и новый запросы через штатные вызовы MCP. Для старого MCP при любой внутренней правке сравнить все RDF-термы, несвязанные поля, кратность и порядок на фиксированной выборке, включая границу лимита MCP.

## 5. Замеры и решение о внедрении

- Использовать только выделенный тестовый экземпляр GraphDB с неизменяемым снимком. Для показательного измерения нужен снимок с сопоставимым объёмом и распределением данных. Подтвердить endpoint и префикс из эффективной конфигурации, отключить обновления на снимке, использовать отдельные процессы и журналы. Любые запросы к боевому репозиторию исключены. При отсутствии стенда выполнить синтетические проверки, подготовить команды и указать блокер для приёмки.
- Запускать A и кандидат последовательно и чередовать их в парных раундах после трёх прогревов. Базовый API использует исходную реализацию. Для каждого варианта собрать 50 холодных HTTP-вызовов с паузой 0,5 с, таймаутом 90 с и фиксированным seed 42, если порядок рандомизируется. Гарантировать промах кеша стендовым способом, например отключением TTL только в тестовых процессах и подтверждением числа фактических SELECT. Один и тот же UTC-момент использовать в проверке данных и сравнении кандидатов.
- Зафиксировать медиану, p95 по ближайшему рангу, максимум, число вызовов дольше 1 с, ошибки и размеры ответов. Для API считать сквозное время, а также время каждого SELECT и общее время работы с GraphDB, число чтений и строк. Не сравнивать задержку одного SPARQL с суммарной задержкой HTTP. При изменении контрольного отпечатка данных признать серию несопоставимой и повторить на подтверждённом снимке.
- Порог для новой страницы: минимум 2× по медиане и p95 холодного API, 50/50 успешных вызовов и прохождение проверок семантики. Для старого MCP отдельная оптимизация требует 2× по медиане и p95 `graphdb_ms`, 50/50 успешных вызовов, полноты таймингов и эквивалентности. После прохождения выполнить полный прогон каталога без `--template`, с отдельным файлом параметров для новых обязательных параметров.
- Приёмка проводится по свежему сопоставимому прогону. Если критерии не выполнены, сохранить прототипы и результаты диагностики, оставив рабочий путь страницы на текущей реализации. При необходимости вынести предварительный расчёт фактов в загрузчике в отдельную задачу с учётом обновлений и удаления исходных сущностей.

Пример для MCP после запуска тестового процесса с отдельным журналом:

```bash
python -m mcp.profile_graphdb --url "$SLA_TEST_MCP_URL" \
  --mcp-log "$SLA_TEST_MCP_LOG" --template lead_lifecycle \
  --warmup 3 --repeats 50 --pause 0.5 --timeout 90 --seed 42 \
  --output logs/lead-response-sla-mcp-baseline.json
```

Результат работы: изменения SPARQL, сервера, страницы и каталога MCP в объёме принятого решения, воспроизводимые команды, JSON каждого прогона и отчёт рядом с историческим бенчмарком. В отчёте указать снимок, версию кода, хеши запросов, агрегаты, расхождения и статус по каждому критерию. Секреты и строки CRM в артефакты не включать.
