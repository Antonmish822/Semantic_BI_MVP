# План сокращения времени ответа AI Agent в CRM Pulse Monitor

Цель — сократить время от отправки вопроса до корректного ответа в дашборде. Первая очередь уменьшает контекст модели и устраняет повторную загрузку схемы в рамках запроса. Следующая очередь сокращает число вызовов модели, ускоряет тяжёлые выборки и улучшает выдачу ответа.

## 1. Исходный профиль и область изменений

Текущий маршрут проходит через `static/agent.js` → `POST /api/agent` в `server.py` → `agent_service.py` → Polza.ai и MCP → GraphDB. Агент получает `tools/list` и при наличии `run_named_query` загружает каталог до первого вызова модели. Один вопрос может пройти через модель для выбора схемы, чтение схемы, модель для построения запроса, выборку и модель для ответа. Результаты инструментов накапливаются в контексте текущего запроса. По умолчанию история ограничена 12 сообщениями, каждое из которых может быть объёмным.

| Показатель | Наблюдение по журналам стенда |
| --- | --- |
| Время API по 116 запросам, включая ошибки и несколько версий | Медиана 11,13 с, p95 41,86 с |
| Доля модели в длительности 86 запросов с финальным текстом | Медиана 98,2% по запросам. Корректность текста отдельно не оценивалась |
| 38 ответов с чтением схемы | Медиана ответа MCP около 160 КБ. Медианный прирост контекста следующего шага — 46,7 тыс. входных токенов. В 11 запросах схему читали повторно |
| Один запрос после запуска текущей сборки | 25,48 с до отображения, 25,36 с на API, 23,03 с в трёх вызовах модели, 0,82 с на схему, 1,46 с на выборку |
| Каталоги инструментов и шаблонов | Медианы 3,2 и 3,5 мс соответственно |

Эти данные задают порядок работ. Для приёмки нужен профиль одной фиксированной версии на одинаковых вопросах. Логику ассистента управления онтологиями, политики видимости данных и API дашборда учитывать как совместимые контракты. Именованные выборки доступны в синтетическом режиме. Рабочие ответы по данным должны использовать разрешённую аналитическую проекцию и действующие проверки MCP.

## 2. Быстрые первоочередные изменения

### P0. Зафиксировать базу и договориться о метриках

1. Зафиксировать ревизию, идентификатор модели, режим MCP, версию схемы, снимок данных, число параллельных запросов и настройки таймаутов. Сохранить фиксированный набор синтетических вопросов и ожидаемых результатов по разделу 4.
2. Использовать существующие события `agent_browser`, `agent_request`, `agent_stage`, `agent_model_result`, `mcp_request` и `safe_sparql`. Сопоставлять их по `request_id`, а связанные вызовы MCP — по номеру вызова и шагу модели. Время GraphDB входит во время MCP.
3. Добавить метаданные, которых не хватает для сравнения. Нужны режим подготовки контекста, его размер по компонентам, размер схемы после сокращения, признак повторного использования результата, тип маршрута и статус инструмента. Считать байты и фактические токены раздельно. Оставлять в журналах только технические метаданные.

### P1. Сократить представление схемы и повторно использовать его в запросе

1. В `agent_service.py` преобразовывать результат `explain_schema` для построения запроса в компактный индекс. Сохранить точные URI, типы, domain/range, нужную иерархию, область графов и статусы полноты. Выбирать релевантные разделы по вопросу и текущему шагу. Сохранять различие между опубликованной схемой и наблюдениями из CSV.
2. Использовать компактное представление в аналитическом маршруте. Для явных вопросов об онтологии, её аксиомах и Turtle выбирать нужный фрагмент или существующий полный режим по назначению вопроса. При неоднозначном выборе предложить уточнение или запросить конкретный фрагмент. При частичной схеме сохранять признак неполноты. Полный контракт `explain_schema` для других потребителей сохранить.
3. На первом этапе преобразовывать существующий MCP-ответ на стороне агента. Это сокращает вход модели и даёт отдельно оценить эффект. Повторный одинаковый вызов `explain_schema` обслуживать из памяти текущего запроса. При запросе более узкого фрагмента использовать уже полученную схему, если нужная часть в ней есть. Раздельно считать вызов, предложенный моделью, и фактический RPC.
4. Ограничить размер компактного индекса и проверить, что важные для запроса связи не исчезают при сокращении. Если лимит мешает выбрать URI или построить корректный запрос, вернуть уточнение либо загрузить нужный фрагмент в пределах бюджета шагов.

### P2. Сократить контекст после выборки

1. Включать в шаг подготовки финального ответа текущий вопрос, нужные сведения из диалога и проверенный результат инструмента. Передавать только поля, необходимые для ответа. Сохранить единицы измерения, период, фильтры, статус, признак усечения и данные по каждой части сравнения. Сохранять ключевые связи схемы для вопросов, где их интерпретация входит в ответ.
2. Включать сокращённый контекст после получения всех нужных результатов, когда типовой сценарий однозначно завершён. Для составного вопроса с недостающими данными оставить переход к следующему разрешённому инструменту. В случае отказа или пустой выборки передавать соответствующий статус. Сохранять текущие поля ответа `/api/agent` и поведение истории в интерфейсе.
3. Ограничить историю, отправляемую модели, по объёму. Сохранить последний вопрос и сведения, нужные для ссылок вроде «а за прошлую неделю?». Если период, объект или фильтр восстановить невозможно, задавать уточняющий вопрос. Отдельно измерять эффект в новой и длинной сессии.
4. Выпустить P1 и P2 раздельно с возможностью переключить режим на стенде. Сравнить исходный вариант, P1 отдельно и P1 вместе с P2. Сохранить переключатель для безопасного отката первой очереди.

## 3. Развёрнутые изменения

| Направление | Реализация и условие применения |
| --- | --- |
| **P3. Маршрут для частых однозначных вопросов** | Выбрать 2–3 сценария по профилю. Описать поддерживаемую метрику, обязательные параметры, допустимые значения и источник данных. Явное совпадение выполнять через утверждённую операцию MCP. Число и простую таблицу формировать из проверенного результата на сервере. Если нужна интерпретация, сделать один вызов модели с компактными данными. Неполный или неоднозначный запрос направлять в обычный цикл либо на уточнение. |
| **P4. Сокращение раундов и повторов** | Проверить нативные вызовы инструментов на используемой связке модели и Polza.ai. Сопоставить частоту ошибок формата, число повторов, корректность и задержку с текущим JSON протоколом. Сохранять серверный список разрешённых инструментов и проверку аргументов. Если поддержки нет, использовать текущий протокол и убрать из подсказок противоречащие инструкции. При исчерпании бюджета шагов возвращать предусмотренный ответ или ошибку с понятной причиной. |
| **P5. Схема на стороне MCP** | Если чтение и передача схемы заметны после P1, добавить компактный запрос схемы или выдачу по разделам в `mcp/mcp_schema.py` и `mcp/mcp_server.py`. Кэшировать опубликованный индекс по источнику, области и версии схемы. Обновлять после публикации, использовать ограниченный TTL для внешних обновлений и объединять конкурентные обновления одного ключа. Проверить переключение источника и версий. |
| **P6. Выборки и параллельность** | Измерить GraphDB отдельно на медленных шаблонах. По профилю ограничивать поля и строки, переносить агрегации в запрос и сокращать дорогие соединения. Контролировать результаты до и после. Объединять или выполнять параллельно только независимые выборки с учётом лимита MCP и GraphDB. Сохранять порядок выдачи инструментов и частичные ошибки. |
| **P7. Таймауты и нагрузка** | Измерить ожидание рабочего потока, сетевое время и хвосты зависимостей. При заметных накладных расходах проверить долгоживущий HTTP-клиент к провайдеру. Согласовать общий бюджет запроса с таймаутами прокси, модели и MCP, резервируя время на ответ. Повторы выполнять в пределах оставшегося бюджета. Кэш каталогов рассматривать, если замеры под нагрузкой покажут заметный выигрыш. |
| **P8. Потоковая выдача** | Делать отдельным этапом, если время до первого текста остаётся большим после сокращения полного времени. Передавать только финальный текст через агента и прокси, сохраняя действующие правила обработки данных. Проверить проксирование без буферизации, отмену запроса, ошибку до и после первого фрагмента и завершение Markdown. Сравнить время до первого текста и время до полного ответа. |

## 4. Проверки и критерии приёмки

| Группа | Что проверять |
| --- | --- |
| Типовые сценарии | Справка без базы, один агрегат, сравнение двух периодов или групп, запрос с чтением схемы, явный вопрос про онтологию, большая или усечённая выдача, старый диалог с уточнением |
| Пограничные сценарии | Неоднозначный период, неизвестный параметр, пустой результат, частичная схема, обновление схемы, отключённый инструмент, отказ политики, неверный формат вызова, таймаут, недоступный MCP, исчерпание шагов |
| Данные и совместимость | Точные значения, фильтры, периоды, единицы и полнота по ожидаемым результатам. Раздельные проверки синтетики и рабочей проекции. Проверить контракт `/api/agent`, корреляцию событий и отсутствие содержимого CRM, промптов и секретов в новых логах |
| Нагрузка | Сначала последовательный прогон. Затем ограниченная параллельная нагрузка с замером очереди, p95, ошибок и нагрузки GraphDB. Холодные и прогретые запросы отражать отдельно |
| Пользовательский интерфейс | Отправка из `/agent`, статусы, появление полного ответа, форматирование таблиц, история, повторный запрос, ошибка и остановка опроса прогресса |

- Сравнивать версии на одном снимке данных, одной конфигурации и одинаковом порядке сценариев или чередовать варианты. Начать примерно с 20 повторов на вариант и сценарий при доступном бюджете. p95 на малой выборке считать предварительным и подтвердить расширенным прогоном для сценариев, влияющих на выпуск.
- Для каждого сценария указать N, медиану и p95 браузера и API, число обращений к модели и MCP, токены, ошибки, таймауты и долю правильных ответов. Раздельно показать успешные ответы и весь поток. Отдельно показать деградации по типам вопросов и разобрать несколько медленных цепочек. Заглушки использовать для функциональных проверок и числа вызовов.
- Стартовые цели для первой очереди — **сократить медианный объём входа следующего вызова после схемы минимум на 50%** и **снизить медиану времени до полного ответа минимум на 20%** на сценариях со схемой. Проверить, что p95 этих сценариев улучшается на достаточной выборке. На остальных сценариях проверять отсутствие воспроизводимой деградации задержки, корректности и успешности. Сверять ответы с фиксированными ожидаемыми результатами. Пороги относятся к будущим замерам.
- Для P3 структурированный ответ должен получаться с нулём вызовов модели, пояснение — максимум с одним вызовом. Любой ошибочный выбор маршрута, обход проверок MCP, потеря признака усечения или неверный итог в обязательном сценарии блокирует включение нового режима.
- Выпускать этапы независимо. Сначала сравнить варианты на стенде, затем включать прошедшие проверку изменения по одному и следить за p95 и долями ошибок. При регрессии переключить соответствующий этап обратно и проверить медленные цепочки.
