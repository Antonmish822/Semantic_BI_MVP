# Безопасное выполнение SPARQL через MCP

## Цель и границы

Агент вкладки AI Agent строит SPARQL для вопросов о сделках, лидах, активностях и сотрудниках. Если подходящего именованного запроса нет, агент вызывает `sparql_select`. MCP принимает ограниченный поднабор SELECT, выполняет его в отдельном аналитическом репозитории GraphDB и возвращает только данные, разрешённые к передаче модели. Опубликованный TBox агент запрашивает через `explain_schema` по необходимости. Пользователи и внешние агенты получают одинаковые ограничения на прямом MCP-входе.

Первый релиз поддерживает агрегаты и соединения между разрешёнными классами. Подробные карточки CRM, поиск по конкретному человеку и выгрузка строк не входят в контракт. Именованные запросы остаются отдельным маршрутом. Их результаты, если они попадают в контекст модели, подчиняются той же политике раскрытия данных.

## 0. Зафиксировать исходное состояние

- Прочитать применимые `AGENTS.md`, этот план и журнал в `ontology_architecture_plan.md`. Проверить Git-статус и сохранить каждый существующий пользовательский diff до правок. Согласовать с текущим состоянием ветки предполагаемые пути ниже.
- Изучить `mcp/mcp_security.py`, `mcp/mcp_server.py`, `mcp/mcp_queries.py`, `mcp/mcp_schema.py`, `agent_service.py`, клиент RDF в `server.py`, `compose.yaml`, `Dockerfile`, `.env.example`, `README_MCP.md`, запросы и тесты. Установить реальные точки входа и потоки данных от GraphDB до MCP, модели, UI и логов.
- На момент подготовки плана `sparql_select` объявлен в MCP, вызов использует общий клиент, проверка и добавление LIMIT находятся в `mcp_security.py`, а размер ответа проверяется после загрузки результата. `AGENT_ALLOW_SPARQL` по умолчанию включён в коде агента. В `agent_service.py` есть пути упаковки результата инструмента для модели, ответа UI и диагностической печати. Перепроверить их до реализации. Снять безопасный baseline контрактов на синтетических данных.

## 1. Утвердить набор данных и полномочия

- Создать на выделенном стенде отдельный репозиторий аналитической проекции. Новому инструменту выдать отдельные права чтения только этого репозитория. URL, имя репозитория и учётные данные получает сервер из своей конфигурации. Клиентский вызов не управляет маршрутом, именем пользователя, графами или параметрами GraphDB. Запретить перенаправления HTTP для нового транспорта и ограничить сетевой доступ MCP к ожидаемому адресу.
- Подготовить явную таблицу доступа, привязанную к версии политики: точные URI графов, классов и предикатов, допустимые соединения, разрешённые измерения, меры, бакеты времени и диапазоны фильтров. Сопоставить её с опубликованным TBox. Поле вне таблицы недоступно, даже если оно есть в TBox. `GRAPH_PREFIX` и CSV дают справочный контекст и не предоставляют разрешений.
- Проекция формируется по белому списку и проверяется перед обновлением. Исключить имена, контакты, свободный текст, секреты, исходные идентификаторы и URI сущностей. Если для связей нужны идентификаторы, использовать внутренние ключи проекции и разрешать их только в соединениях. Определить единицу подсчёта и кардинальности связей, чтобы, например, связь с несколькими активностями не увеличивала число сделок. Зафиксировать расписание, атомарность обновления, версию снимка и максимально допустимый возраст. Пустая, отсутствующая, просроченная или неподтверждённая конфигурация не разрешает запуск инструмента. Валидная пустая выборка возвращает успешный пустой результат.
- Ограничить раскрытие агрегатов. Разрешить заранее определённые разрезы, фиксированную гранулярность, минимальный размер группы по числу отдельных сущностей (стартовый кандидат — 10) и контролируемое множество фильтров. Учитывать восстановление малых групп из разности похожих ответов, итогов и детализации. Для чувствительных метрик использовать заранее рассчитанные безопасные ячейки с согласованной политикой подавления или исключить метрики из свободных запросов. Утвердить политику и фактический набор графов с владельцем данных перед включением на реальных данных. Синтетический стенд можно реализовать параллельно с согласованием.
- Зафиксировать режим вывода. Начать без выведенных данных и проверить поведение фактической версии GraphDB. Для режима с выводом использовать отдельно проверенную проекцию и повторить проверку области и раскрытия. Опубликованные аксиомы сами по себе не гарантируют доступность классификации экземпляров.

## 2. Реализовать серверную проверку и построение запроса

- Сохранить имя `sparql_select` и аргумент `query: string`. Ограничить тело запроса и длину SPARQL в байтах, отклонять неожиданные аргументы и типы. Использовать SPARQL-парсер и фиксированную проверенную версию зависимости. Обработать всё дерево запроса, разрешить только известные узлы и позиции, ограничить глубину и число узлов. Ошибку парсинга и неподдержанный узел возвращать до сетевого вызова.
- Первый поднабор описать в документации и в машинных метаданных. Разрешить явный SELECT с разрешёнными агрегатами, предикатами, соединениями, группировками и простыми типизированными фильтрами. Нормализовать префиксы до сравнения URI. Ограничить число троек, соединений, измерений и агрегатов. Проверять связность паттерна и назначение каждой переменной, включая фильтры, сортировку, выражения и группировку. Разрешённые агрегаты привязать к утверждённой семантике, например `COUNT(DISTINCT ...)` для подсчёта сущностей.
- Явно отклонять обновления, прочие формы запросов, федерацию, заданный клиентом dataset, выбор графа клиентом, переменные в позиции предиката, `SELECT *`, пути свойств, подзапросы, произвольные функции и прочие конструкции вне поднабора. OFFSET отключить в первом релизе. Для разрешённых узлов построить собственное небольшое типизированное представление и сформировать из него новый запрос. Отправка исходного текста и строковая правка произвольного SPARQL исключены. URI выводить из доверенной таблицы, литералы сериализовать штатным RDF-кодом.
- Сервер назначает точный dataset и проверяет область на фактической версии GraphDB. Выбрать документированный механизм протокола или серверные dataset clauses, закрепить один вариант и проверить, что запросы не видят граф по умолчанию или другие именованные графы. Выделенный репозиторий содержит только утверждённую проекцию и служит независимой границей. Сервер ограничивает верхний LIMIT даже при явно большем лимите клиента. Сохранить меньший пользовательский LIMIT, а при превышении серверного окна выдавать прозрачный признак усечения. При необходимости читать одну дополнительную строку в пределах отдельного жёсткого лимита.

## 3. Ограничить выполнение и раскрытие результата

- Добавить для динамического SELECT узкий клиент GraphDB. Можно переиспользовать проверенные части транспорта, но чтение ответа должно останавливаться по пределу байтов до полной загрузки и разбора. Ограничить распакованный объём либо отключить сжатые ответы. Валидировать тип ответа, структуру SPARQL JSON, размер ячейки, число строк, итоговый размер MCP-конверта и разрешённые колонки, типы и значения. Не отправлять наружу неожиданную колонку, значение неизвестного измерения или скрытый технический столбец.
- Начальные значения для синтетического стенда: 16 КиБ SPARQL, 100 возвращаемых строк, 256 КиБ ответа GraphDB, 64 КиБ результата для агента, два параллельных запроса на процесс, пять секунд на сервере GraphDB и восемь секунд на запрос MCP к базе. Зафиксировать единицы, корректные диапазоны настроек и общий бюджет за ход агента. Дедлайн должен учитывать медленное чтение и отмену запроса. Ограничить скорость по проверенной личности вызывающего и общий параллелизм на развёртывание. При перегрузке отвечать сразу или с ограниченной очередью. Применить соответствующие версии GraphDB параметры таймаута и настроить ошибку вместо частичного успеха при таймауте.
- Ограничить доступ к MCP между сервисами и аутентифицировать вызывающего при прямых вызовах. Права и квоты проверяются на MCP для каждого вызова. Сообщения пользователя и системный промпт не задают полномочий. В диагностике оставлять ID запроса, проверенный идентификатор клиента, версию политики, исход, длительность, число строк и байтов. Убрать печать сырых результатов и сырые ошибки GraphDB. Проверить доступ к журналам провайдера, отладке агента, истории и UI.
- Сохранить `bindings` для успешного вызова и добавить метаданные: признак усечения, эффективный лимит, снимок проекции и режим вывода. Для отказов дать стабильные машинные причины, например `disabled`, `invalid_query`, `unsupported_query`, `scope_denied`, `rate_limited`, `timeout`, `response_too_large`, `upstream_unavailable`. Отделить ошибки JSON-RPC от ошибок выполнения инструмента согласно текущему контракту MCP. Ответы об ошибках не содержат подробностей транспорта или секретов.

## 4. Подключить AI Agent и выпуск

- Добавить независимые флаги MCP и агента с безопасными значениями по умолчанию. Например, `MCP_ENABLE_SAFE_SPARQL=0` и `AGENT_ALLOW_SPARQL=0`. Скрывать отключённый инструмент в `tools/list` и проверять флаг на прямом `tools/call`. Удалить старый динамический маршрут после подключения нового. Отсутствие аналитического репозитория не переключает запрос на основной CRM-репозиторий. Именованные запросы и чтение TBox продолжают работать при выключенном инструменте с учётом политики данных для агента.
- Обновить системный промпт и пример его переопределения в `.env.example`. Агент выбирает подходящий именованный шаблон, при необходимости запрашивает TBox и разрешённые возможности выборки, строит новый SELECT только при наличии инструмента. Схема нужна при неизвестном URI, связях, соединениях или создании нового запроса. Не подгружать TBox автоматически. При неподдержанном запросе агент выбирает подходящий шаблон, уточняет вопрос или сообщает ограничение. Таймаут и усечение передаются пользователю как таковые. Значения из инструмента трактуются как данные.
- Обновить README и сборку. Развести секреты и настройки сервисов так, чтобы MCP динамической выборки не наследовал административные полномочия. Задокументировать включение и быстрый откат двумя флагами. Выкатывать сначала на синтетический стенд, затем на одобренную проекцию. При откате оставить динамическую выборку выключенной.

## 5. Проверки и критерии приёмки

| Уровень | Подтверждение |
| --- | --- |
| Парсер и построитель | Разрешённые агрегаты и соединения формируют ожидаемый запрос. Неподдержанные формы, структуры и URI дают отказ без HTTP. Комментарии, регистр и префиксы соблюдают правила SPARQL. Проверены LIMIT, типы аргументов, размер и глубина. |
| Транспорт и политика ответа | Поддельный endpoint покрывает дедлайн, медленное чтение, лимиты байтов и строк, неверный JSON, неожиданные колонки, ошибки сети, усечение и перегрузку. Журналы и ошибки не содержат исходного SPARQL, содержимого результата и секретов. |
| Выделенный GraphDB | Синтетические разрешённые и закрытые графы имеют различимые контрольные значения. Проверить фактический dataset, read-only права и границы аккаунта, режим вывода, дедлайн и отсутствие ошибочного частичного успеха. Проверки прав записи только на выделенном репозитории и через штатную процедуру контроля доступа. |
| MCP и агент | Реальные `tools/list` и `tools/call` проверены с обоими положениями флагов. Заглушка модели проходит последовательность «запросить схему по необходимости → построить SELECT → получить допустимый агрегат». Покрыть прямой вызов MCP, отказ, статусы для UI и сохранение работы именованных запросов. Проверить фактический payload модели и UI на синтетических маркерах. |
| Выкатка | Результат сверяется с известными контрольными агрегатами. Владелец данных одобрил графы, разрешённые поля, правила раскрытия и назначение учётной записи. Команды включения и отката проверены на выделенном стенде. До этого динамический инструмент выключен для реальных данных. |

Справка по dataset и таймаутам. Проверить документацию версии, установленной на стенде. [SPARQL 1.1 Protocol](https://www.w3.org/TR/sparql11-protocol/) · [GraphDB 11.5, настройка репозитория](https://graphdb.ontotext.com/documentation/11.5/configuring-a-repository.html)

## Минимальные доработки до первого выпуска

Цель первого выпуска — агент через MCP получает проверенный агрегат `COUNT(DISTINCT)` со стенда с синтетическими данными. Для первого выпуска достаточно утверждённых форм запроса с одной мерой, простыми соединениями и максимум одним измерением. На рабочей CRM оба флага остаются выключенными до выполнения условий ниже.

1. **Проверять дерево SPARQL.** Взять текущий поднабор за основу. Зафиксировать проверенную версию парсера, проверять типы аргументов, размер тела и SPARQL, глубину и число узлов. Преобразовывать только явно поддержанные узлы в типизированное представление. Привязывать меру к классу, а измерение и допустимые связи — к точным URI из политики. Собирать запрос с серверным `FROM` и принудительным `LIMIT`. Публиковать доступные формы в метаданных инструмента.

   Готово, когда допустимые запросы с префиксами и комментариями дают ожидаемый запрос GraphDB, а неподдержанные узлы, неизвестные URI и превышение лимитов отклоняются до HTTP.

2. **Закрыть правила раскрытия.** Для каждой меры разрешить конечный список форм запроса и бакетов. Утвердить, какие итоги и разбивки можно показывать вместе. Если по итогам и разбивке можно вычислить скрытую группу, исключить одну из форм либо отдавать заранее подготовленные ячейки с согласованным подавлением. Валидировать колонки, типы и значения перед выдачей. Сохранить каталог и маршрут именованных запросов. Допускать в контекст агента только отдельно утверждённые агрегатные шаблоны через тот же контроль результата. Для остальных возвращать `data_policy_unapproved`.

   Готово, когда проверка каждой разрешённой комбинации подтверждает правила раскрытия, а синтетические маркеры сырых строк, идентификаторов и секретов отсутствуют в контексте модели, ответе UI и журналах приложения.

3. **Довести ограничения вызова.** Применять единый дедлайн к запросу GraphDB от начала соединения до полного чтения ответа. На GraphDB установить таймаут с ошибкой и проверить завершение запроса. Зафиксировать бюджет вызовов за ход агента, квоту по проверенной личности MCP и общий предел параллелизма развёртывания. Для первой выкладки достаточно одного процесса MCP, если квота и параллелизм действуют на весь этот экземпляр. Разделить секреты MCP, агента и dashboard в конфигурации развёртывания. Ограничить исходящие соединения MCP настроенными адресами хранилищ.

   Готово, когда медленный ответ, превышение лимитов и перегрузка дают контролируемый отказ. Таймаут на выделенном GraphDB не даёт успешных `bindings`, а проверка состояния запроса подтверждает его завершение.

4. **Повторить сквозную приёмку.** На отдельном GraphDB с синтетическими данными и учётной записью только для чтения пройти из браузера сценарий с заглушкой модели `explain_schema` → новый SELECT → ожидаемый агрегат. Проверить область данных, оба флага, прямой MCP-вызов, откат, пустой результат, усечение и отображение отказов в UI. Сохранить результаты в журнале. Отдельно учесть ошибки существующего набора тестов помощника онтологии и определить, затрагивают ли они изменённый маршрут.

   Готово, когда сценарий воспроизводится из браузера и через прямой MCP-вызов, а отключение серверного флага блокирует выборку независимо от настроек агента.

5. **Подготовить первую реальную проекцию после согласования.** Владелец данных утверждает точные графы, поля, разрешённые формы запроса и правила совместного раскрытия. Загрузчик формирует проекцию по белому списку, проверяет её до публикации и атомарно переключает снимок. MCP сверяет версию и возраст опубликованного снимка и выполняет запросы только с отдельной учётной записью на чтение. Включение реальной проекции требует отдельной приёмки.

Расширение языка запросов, дополнительные меры, фильтры, измерения и режим с выводом можно планировать после первого выпуска.
