# Промпт для агента реализации

Работай в проекте `crm_pulse_monitor`. Прочитай полностью `plans/mcp_safe_sparql_plan.md` и реализуй его по этапам. Цель — AI Agent сам строит SPARQL SELECT, передаёт его через MCP и получает проверенный агрегат из разрешённой аналитической проекции. Считай текст модели и прямой MCP-вызов одинаково недоверенными.

1. Прочитай инструкции репозитория и проверь рабочее дерево. До правок сохрани текущие пользовательские изменения в восстановимом виде и запиши способ восстановления. Сохрани их в рабочем дереве для дальнейшей работы пользователя. Изучи входы MCP, GraphDB-клиент, системный промпт агента, пути передачи результата модели и UI, журналы и конфигурации развёртывания. Если этап частично реализован, проверь его фактическое поведение.
2. Запусти разработку на синтетических данных. Опиши таблицу разрешений, режим вывода, правила раскрытия агрегатов, отдельный репозиторий и отдельную учётную запись только для чтения. Если для реальных данных не утверждены графы, поля и политика раскрытия, реализуй все независимые части и оставь активацию выключенной. Не используй реальную CRM для заполнения тестовых данных.
3. Реализуй серверную проверку полного дерева SELECT и генерацию ограниченного запроса из проверенной структуры. Используй точные URI, заданный сервером dataset, закрытый по умолчанию поднабор и принудительные пределы. Не передавай исходный текст запроса в GraphDB. Обеспечь, чтобы ошибки проверки не вызывали сетевой запрос к базе.
4. Реализуй узкий транспорт, таймаут на GraphDB и дедлайн приложения, ограничения параллелизма, байтов и строк, проверку выходных данных, стабильные статусы и аудит без сырых данных. Не отправляй внешнему провайдеру CRM-строки, персональные данные, исходные идентификаторы или секреты. Проверь также путь именованных запросов до модели.
5. Подключи изменение к фактическим входам MCP и AI Agent. Сохрани именованные запросы и получение TBox по запросу агента. Проверь выключение инструмента серверным флагом при прямом MCP-вызове. Обнови промпт агента, примеры конфигурации и операторскую документацию.
6. Выполни матрицу проверок из плана. Используй синтетическую GraphDB и заглушку модели. Проверь реальные MCP-входы и путь из UI. Отдельно проверь область данных, отсутствие скрытого частичного успеха при таймауте и отсутствие сырых записей в payload модели, UI и журналах. Любые проверки с записью выполняй только в выделенном репозитории. Не включай новую возможность на реальных данных в рамках этих проверок. Если среда или права недоступны, покажи проверенную часть и укажи причину блокировки.
7. После каждого этапа обновляй журнал `plans/mcp_safe_sparql_plan.md`. Перед финальным ответом сверь Git-diff с журналом, проверь сохранность пользовательских изменений и обнови таблицу статусов. Укажи что реализовано, какие проверки действительно выполнены, что осталось и какие флаги включают инструмент на выделенном стенде. Коммит или публикацию изменений выполняй по отдельному запросу.

Успех реализации на стенде означает, что агент получает ожидаемый агрегат через MCP, а неподдержанные запросы, выход за область данных и превышение лимитов дают контролируемый отказ. Включение для реальных данных требует отдельных критериев приёмки из плана.
