# План развития компонента «Онтология»

## Цель

Веб-интерфейс, MCP и агент генерации аксиом используют общие операции чтения онтологии. Перед генерацией агент получает актуальный опубликованный TBox и агрегаты по связанным данным CRM, а также учитывает редакцию TTL, к которой будет применено предложение. Редактирование файла, проверка предложения и публикация в GraphDB остаются самостоятельными действиями.

## Исходное состояние

- `ontology_admin.py` валидирует Turtle, сохраняет файлы с проверкой SHA-256 и публикует их в именованные графы GraphDB со сверкой после записи.
- `server.py` формирует запросы для `POST /api/ontologies/class-statistics`. Вход — namespace, ответ содержит классы, заполненность признаков и связи.
- `ontology_assistant.py` уже имеет инструменты чтения файлов, графов и отдельных профилей данных. Генерация зависит от внешнего провайдера модели.
- MCP работает в отдельном контейнере. Его `explain_schema` читает локальные справочные файлы. Каталог пользовательских TTL подключён к веб-приложению.

## Этап 1. Общие операции чтения и MCP

1. Выделить Python-пакет `ontology` с модулями `schema` и `statistics` и общим адаптером чтения RDF-хранилища. Веб-обработчик и MCP передают ему проверенные параметры, а модуль возвращает структурированные результаты и ошибки. Использовать существующий клиент RDF и учесть оба поддерживаемых бэкенда там, где они уже обслуживают статистику.
2. Получать определения классов, свойства, `subClassOf`, `domain`, `range` и применимые OWL-выражения из опубликованного графа. Разрешённые онтологии и область данных определяются серверной конфигурацией или реестром. Сопоставить `slug`, URI графа и namespace явно. Схема может охватывать несколько namespace, поэтому не выводить namespace из `slug` механически.
3. Для статистики явно определить область CRM-данных и режим учёта выведенных типов. До переключения сравнить результаты со штатным REST API и зафиксировать смысл счётчиков. Сохранить существующий запрос по namespace и поля ответа для текущего интерфейса. Если целевая область подсчёта меняет прежние цифры, ввести явный новый режим и описать различие.
4. Добавить доступные только для чтения MCP-инструменты:
   - `list_ontologies()` — опубликованные онтологии, их `slug` и URI графов.
   - `describe_ontology(slug, class_uri?)` — определения и аксиомы опубликованной схемы с ограничением объёма.
   - `ontology_class_statistics(slug, class_uri?)` — счётчики экземпляров, заполненность свойств и сведения об области подсчёта. Состав результатов и формулы совпадают с REST при одинаковой области и параметрах.
5. Добавить метаданные чтения: `graph_uri`, подтверждённая ревизия или отпечаток прочитанного графа, время чтения, область данных и режим вывода, где применимо. Отдельно обозначать пустой, усечённый, частичный и недоступный результат. Для ограниченных ответов дать способ уточнить запрос по классу. Если источник статистики не обеспечивает единый снимок нескольких SELECT, указывать интервал чтения. Сохранить совместимость `explain_schema` и существующих инструментов каталога запросов.

## Этап 2. Файлы, ревизии и публикация

1. Вынести работу с TTL, именованными графами и публикациями в модули `files`, `graphs` и `publication` общего пакета. Переиспользовать проверку slug, валидацию Turtle, атомарную запись и проверку ожидаемого SHA-256.
2. Хранить неизменяемые сохранённые ревизии TTL и журнал публикаций в постоянном хранилище приложения. Зарегистрировать существующие файлы и именованные графы с сохранением slug и URI вида `urn:bitrix24:ontology:<slug>`. Текущую опубликованную ревизию подтверждать сравнением RDF-графов с учётом пустых узлов. При несовпадении показывать расхождение.
3. Публиковать явно выбранную сохранённую ревизию по `slug` и SHA-256 в стабильный именованный граф. Сериализовать публикации одной онтологии. После записи прочитать граф и сверить результат. При неоднозначном результате сначала сверить состояние GraphDB и завершить запись в журнале по фактическому результату. Откат оформлять как новую публикацию предыдущей ревизии. Хранить историю TTL вне рабочего RDF-набора, чтобы старые версии не участвовали в выводе.
4. В UI показать SHA-256 сохранённого TTL, статус опубликованной версии и состояние операции. Сохранить текущие авторизацию и маршрут публикации. MCP читает опубликованную схему из GraphDB без подключения тома черновиков и без полномочий на запись.

## Этап 3. Обязательный контекст для агента аксиом

1. **Перед каждым запуском генерации** сервер сам загружает актуальную схему из опубликованного графа и статистику для затронутых классов или свойств. Начальный контекст должен передаваться модели независимо от того, решила ли она вызвать инструмент. При неоднозначном запросе использовать ограниченную сводку, затем разрешать агенту уточнять классы и свойства через инструменты чтения.
2. Основной вариант интеграции — прямой вызов общего пакета из `ontology_assistant.py`. Для агента, который работает в другом процессе или подключается извне, предоставить те же операции через MCP. Адаптеры используют один контракт, фильтры, лимиты и разрешённые области данных. Встроенные профили свойств и классификации сохранить как дополняющие операции. Модели передавать определения, допустимые метаданные и агрегаты, исключая строки CRM, персональные данные и секреты.
3. Различать опубликованную схему, сохранённую базовую ревизию и несохранённый текст редактора. Передавать модели их происхождение и идентификаторы раздельно. Для новой онтологии явно показывать отсутствие опубликованной версии и использовать проектный каталог и доступные агрегаты настроенной области. При ошибке чтения указать, какая часть контекста отсутствует. Числовые выводы и выводы о текущей схеме без соответствующих данных блокировать. Если контекст необходим для самого предложения, выдавать статус о недостатке данных.
4. Связать предложение с хешем базы, отпечатком опубликованной схемы и метаданными статистики. Возвращать добавляемые и удаляемые аксиомы, обоснование, использованные данные и ограничения оценки. Сервер формирует и валидирует итоговый Turtle и вычисляет RDF-разницу с учётом пустых узлов. При изменении базы или опубликованной схемы до применения предложить пересчёт.
5. Для аксиом, влияющих на вывод, добавить проверку на изолированном репозитории с тем же набором правил, что у рабочего GraphDB. Сравнивать типизацию и пересечения до и после на одном наборе данных. Если стенд недоступен, обозначить эффект как непроверенный. Пользователь применяет предложение в редакторе, затем отдельно сохраняет и публикует.

## Критерии приёмки

- REST и MCP возвращают одинаковые счётчики при одинаковых фильтрах, области данных и режиме вывода. Проверены нулевая статистика, усечение и недоступность RDF-хранилища.
- После публикации новой ревизии следующий запуск агента получает обновлённую схему и текущую статистику, даже если модель не вызывает ни одного инструмента. Несохранённый TTL и опубликованная схема различимы в контексте.
- Устаревшее предложение нельзя применить как актуальное. Для частичного или недоступного контекста агент не выдумывает аксиомы текущей схемы и статистику. По ответу видно, какие источники использованы.
- На изолированном стенде проверены публикация конкретной ревизии, расхождение файла и графа, неоднозначный результат записи, восстановление статуса и откат. Штатные сценарии UI и существующие инструменты MCP работают по своим контрактам.
