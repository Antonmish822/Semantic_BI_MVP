# Профиль задержек AI-агента — базовый этап

Дата: 2026-11-19. Ветка: `AI_Agent`.

## Изменения

- `server.py`: генерирует/принимает UUID `request_id`; пишет JSON-события с полной длительностью API, исходом, количеством вызовов, контекстом в байтах и размером HTTP тел. На каждый запрос Polza.ai фиксирует шаг, исход, длительность, размеры тел и доступные счётчики токенов. Учитывается HTTP ошибка и таймаут.
- `server.py`: каждый вызов MCP получает `X-Request-ID`, номер вызова и имя инструмента. Учитываются JSON-RPC ошибки внутри HTTP 200 и сбой транспорта.
- `mcp/mcp_server.py`: события MCP включают ID/номер шага, метод, инструмент, размер результата, исход; `run_named_query` и `sparql_select` пишут время `store.select()`, число строк и размер результата. В журнал попадает только имя шаблона из каталога.
- `static/agent.js`: измеряет `performance.now()` от отправки до добавления ответа в DOM, передаёт ID, статус HTTP и класс ошибки в журнал агента.
- Удалены небезопасные отладочные распечатки `AGENT_DEBUG` и `MCP_DEBUG`, которые могли записывать аргументы или полный MCP payload.

События записываются в JSONL-файлы. В них нет текстов сообщений и ответов, аргументов, SPARQL или значений CRM. Идентификатор браузера проверяется по формату UUID.

Локальная проверка обработчика прошла на заглушках: успешная цепочка с двумя ответами модели и одним инструментом вернула тот же `request_id` (API 200); отказ MCP дал API 502 и итоговое событие с тем же ID. Отдельный вызов GraphDB заглушки проверил успешное событие `store.select()` и ошибку, включая ID, номер вызова, число строк и отсутствие CRM значений в журнале. Проверены синтаксис Python (`py_compile`), JavaScript (`node --check`) и `git diff --check`. В репозитории нет исходников тестов для `unittest discover`.

В Docker Compose сейчас нет запущенных контейнеров, поэтому локальный MCP/GraphDB недоступен. Также в плане не определён проверяемый синтетический набор данных и ожидаемые ответы. Не выполнялась платная серия запросов к модели: без тестового набора нельзя достоверно оценить корректность, а 20 повторов на пять сценариев имеют стоимость.

## Как снять базовый профиль

1. Поднять тестовое окружение с отдельным синтетическим GraphDB и MCP; задать ключ, модель, лимиты и таймауты в окружении процесса (не включать debug-режимы). Для файла `.env.ai-agent` запустить в двух терминалах `CRM_MONITOR_ENV_FILE=.env.ai-agent python -m mcp.mcp_server` и `CRM_MONITOR_ENV_FILE=.env.ai-agent python server.py`. Второй процесс использует `DASHBOARD_PORT` (по умолчанию 8082). Убедиться, что GraphDB доступен по тестовой конфигурации.
2. Открыть `/agent` в браузере. События API и браузера читать из `logs/agent-profile.jsonl`, события MCP и GraphDB — из `logs/mcp-profile.jsonl`.
3. Для каждого из пяти сценариев из плана отправить 20 последовательных запросов с фиксированными вопросами и критериями ответа; один сценарий выполнить в новой сессии и в заранее заполненной длинной истории. Выполнить такой же контрольный прогон именованных запросов MCP отдельно. Сопоставлять все события только по UUID.
4. Свести медиану и p95 для API и браузера, длительности каждого этапа, число вызовов, токены/байты/строки, доли транспортных/JSON-RPC/агентных ошибок и ответов, прошедших критерии. Отсортировать `agent_request.duration_ms` и восстановить этапы медленных запросов по UUID.

## Сбор журналов после проверки инструментирования

Прежние команды запуска Python теперь сами создают журналы. При запуске
каждый процесс печатает путь к своему файлу. Файлы дополняются при перезапуске.

- `logs/agent-profile.jsonl` содержит события API, модели, исходящих вызовов MCP и браузера.
- `logs/mcp-profile.jsonl` содержит события MCP и GraphDB.
- `AGENT_PROFILE_LOG_DIR` задаёт другой каталог. Для отдельной серии укажите обоим процессам одинаковый новый каталог.
- В Docker Compose файлы сохраняются в томе `profile_logs`. После сборки их можно читать внутри контейнера, например `docker compose exec crm-pulse-monitor tail -n 20 /app/logs/agent-profile.jsonl`.

После обновления сервера перезагрузите страницу `/agent`, чтобы браузер загрузил
новую версию скрипта. Браузер передаёт технический замер на тот же сервер после
обновления DOM. При недоступности сервера доставка браузерного события может
не состояться.

| Событие | Как читать |
| --- | --- |
| `agent_browser` | От отправки до обновления интерфейса, HTTP-статус или фаза сбоя |
| `agent_request` | Время API, HTTP-статус, тип фактически возвращённого ответа, число вызовов и объём истории |
| `agent_stage`, модель | Время каждого шага, HTTP-статус, байты запроса и ответа, токены при наличии |
| `agent_model_result` | Классификация результата каждого шага и признак повтора |
| `agent_stage`, MCP | Полное время RPC со стороны агента, HTTP-статус, код JSON-RPC и номер связанного шага модели |
| `mcp_request` | Серверная часть RPC, имя инструмента и известного шаблона, размеры, результат обработки |
| `graphdb_select` | Время внутри MCP, строки и байты результата, класс сбоя |

Соединяйте события по `request_id`. У MCP шаг 0 соответствует `tools/list` и входит в общий счётчик API. Последующие шаги MCP соединяются с `mcp_request` и `graphdb_select` по паре `request_id` и `step`. Время GraphDB уже входит во время MCP. Считайте HTTP 200 с `reply_kind=tool_call`, `disallowed_tool_call`, `native_tool_call` или `malformed_tool_call` отдельно от финального текста. Корректность финального текста оценивайте по ожидаемым ответам сценария.

Локальная проверка через HTTP с заглушками дала 37 событий на семи запросах.
Проверены финальный текст, возврат вызова инструмента при исчерпании шагов,
JSON-RPC ошибка внутри HTTP 200, таймаут модели, невалидный JSON от модели,
прямой `sparql_select` и произвольные поля MCP. Контрольное приватное значение
не попало в журналы. Эти результаты проверяют состав событий и их корреляцию.
