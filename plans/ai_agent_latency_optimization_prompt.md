# Промпт для доработки AI Agent в CRM Pulse Monitor

```text
Доработай флоу AI Agent в репозитории crm_pulse_monitor. Цель — сократить время от отправки вопроса на /agent до корректного ответа. Прочитай plans/ai_agent_latency_optimization_plan.md и используй его как план реализации и проверки.

Начни с фактической цепочки static/agent.js → прокси /api/agent в server.py → agent_service.py → Polza.ai и MCP → GraphDB. Проверь инструкции репозитория и состояние рабочего дерева. Сохрани текущие пользовательские изменения. Используй настроенный изолированный синтетический стенд для сквозных проверок.

1. Зафиксируй базу P0. Укажи ревизию, модель, режим MCP, версию схемы и снимок данных. Подготовь вопросы и проверяемые ответы по матрице из плана. Переиспользуй существующие профильные события. Добавь недостающие технические поля для сравнения вариантов, если без них нельзя объяснить результат. Сопоставляй браузер, API, модель и инструменты по request_id и номерам вызовов. Отдельно учти ошибки, таймауты и отказы инструмента. Время GraphDB входит во время MCP.

2. Реализуй P1 отдельным изменением. Передавай модели компактную проекцию результата explain_schema для построения выборок. Сохрани точные URI, типы, необходимые связи, область графов, версию схемы и признаки неполноты. Поддержи явные вопросы об онтологии и точечную детализацию, если компактного представления мало. Переиспользуй результат одинакового обращения к схеме в пределах одного запроса. Сохрани полный контракт explain_schema для других потребителей.

3. Реализуй P2 отдельно. Для завершённой выборки сформируй компактный контекст ответа из релевантного вопроса и истории, проверенных фактов и статусов всех необходимых инструментов. Сохрани фильтры, периоды, единицы, состав сравнения и признаки усечения. Для вопросов, которым нужны дополнительные данные, сохрани инструментальный цикл. Ограничь объём истории, отправляемой модели. Проверь ссылки на предыдущие сообщения и уточнения. Сохрани контракт /api/agent, работу прогресса и историю в интерфейсе. Обеспечь переключение вариантов первой очереди на стенде.

4. Сравни исходный флоу, P1 и P1+P2 по разделу 4 плана. Проверь значения и формулировки ответов по ожидаемым данным, обработку частей сравнения, пустых и усечённых результатов, ошибок и таймаутов. Отдельно проверь, что агент сокращает контекст и делает только один одинаковый запрос схемы внутри обращения. Выполни тесты проекта, целевые тесты затронутой логики и сквозную проверку через /agent на изолированном стенде. Используй заглушки для функциональных проверок и подсчёта вызовов, скорость провайдера измеряй отдельным сопоставимым прогоном. Если нет настроенного провайдера или разрешения на платный прогон, выполни доступные проверки, зафиксируй пробел и дай точные команды для повторения.

5. После сравнения первой очереди выполняй развёрнутые этапы P3–P8 отдельными изменениями по условиям плана. Начни с маршрута для 2–3 однозначных вопросов и снижения повторов модели. Выполняй операции через разрешённые инструменты MCP. Для однозначного запроса проверь ответ без модели или с одним вызовом для пояснения. Для неоднозначного запроса проверь правильное уточнение или переход в общий флоу. Нативные вызовы инструментов включай после подтверждения совместимости используемой модели и провайдера. Кэш схемы, изменения GraphDB, сетевого слоя и стриминг оценивай по измерениям соответствующих участков.

6. Сохраняй границы между синтетическим репозиторием и рабочей аналитической проекцией, действующие проверки инструмента и политику раскрытия данных. В журналы и отчёт включай идентификаторы запросов и технические метаданные. Исключи секреты, исходный SPARQL, тексты вопросов и ответов, значения CRM и содержимое переменных окружения. Развёртывание в рабочей среде оставь отдельным шагом.

В итоговом отчёте перечисли изменённые файлы и режимы переключения, выполненные проверки, команды запуска и результаты по сценариям. Для каждого результата укажи N, медиану, p95, число обращений к модели и MCP, объём контекста и доли правильных ответов и ошибок. Покажи как минимум один пример разложения медленного запроса по этапам. Укажи, какие цели плана выполнены, какие ещё требуют замеров, какие этапы отложены по результатам и как откатить включённые изменения. Отдели измеренный эффект от прогнозов.
```
