# Промпт для агента по переработке страницы «Лиды»

```text
Работай в проекте crm_pulse_monitor. Прочитай plans/lead_response_sla_redesign.md целиком и выполни план. Цель — ускорить холодный GET /api/lead-pulse и сделать основным показателем страницы долю лидов с первой зафиксированной активностью в течение двух часов. Сохрани среднее время реакции как дополнительный показатель, счётчики за 1/7/30 дней, график конверсии по воронкам и очередь красных лидов по всей истории.

1. Проверь инструкции проекта, рабочее дерево и потребителей API и MCP. Сохрани имеющиеся изменения пользователя. Используй logs/graphdb-benchmark-4.json как исторический ориентир и учитывай исправление в logs/lead-lifecycle-optimization-report.md. Прошлые B и C фактически запускали исходный SPARQL. Полный исходный прогон пересёкся с изменением данных.

2. Используй только выделенный тестовый экземпляр GraphDB с неизменяемым снимком. Перед запуском подтверди по эффективной конфигурации endpoint, репозиторий и префикс графов. Не отправляй запросы в боевой репозиторий. Если стенд недоступен, подготовь варианты и проверки на синтетических данных, команды для продолжения и отчёт о блокере. Не заявляй ускорение по синтетике и не переключай рабочую страницу без приёмочных замеров.

3. Сделай узкую выборку лидов и первых активностей для тренда и счётчиков. Для тренда используй 119 дней входной истории и один фиксированный UTC-момент на весь ответ. Проведи ограничение по лидам внутрь соединения с активностями и агрегации. Отдельно сделай выборку красных лидов за всю историю. Проверяй любую связанную сделку и наличие активности в первые два часа. Обогащай справочниками только финальный топ‑10, один элемент на URI, со стабильным порядком при одинаковой дате. Не обрезай кандидатов до проверки условий.

4. Реализуй формулы и оговорённые изменения семантики из раздела 2 плана. Знаменатель SLA включает только лиды 30-дневной когорты, у которых прошли два часа. Активность ровно через два часа засчитывается. Лиды без активности после истечения двух часов входят в знаменатель как нарушение. Критерии сделки и статуса относятся к очереди, а среднее время реакции имеет свою выборку. Проверь все 90 точек и синтетические пограничные случаи из плана.

5. Подключи кандидата через обычный API и интерфейс. Проверь кеш, совместимость формы ответа, правила smart view и отображение пустых данных. Добавь отдельный именованный MCP-запрос lead_response_sla с явным обязательным as_of и описанием в README_MCP.md. Сохрани контракт существующего lead_lifecycle. Любую оптимизацию старого MCP-запроса оцени отдельным прогоном с доказательством эквивалентности. При построении диагностических вариантов делай замену до подстановки префикса и проверяй, что результирующий SPARQL изменился.

6. На стенде измерь A и варианты по 5–10 вызовов. Затем сними финальное сравнение полного холодного API: три прогрева и 50 измерений на вариант, пауза 0,5 с, таймаут 90 с, фиксированный seed 42 для рандомизации. Подтверди промах кеша по фактическим SELECT. Измеряй end-to-end API и GraphDB по отдельности. Если снимаешь onto:explain и onto:measure, запускай их вне обычной серии. Для нового пути требуются 50/50 успешных вызовов, медиана и p95 минимум вдвое ниже свежей базы и проверенная семантика. После приёмки проверь штатные вызовы и повтори полный бенчмарк каталога MCP с параметрами для нового запроса.

7. Внеси принятый вариант в рабочий путь только при выполнении критериев плана. Сохрани JSON каждого прогона и итоговый отчёт рядом с историческим бенчмарком. Для каждого сравнения укажи условия, команды, число строк и байтов, медиану, p95, максимум, число вызовов дольше секунды, ошибки и полноту таймингов. Приведи все расхождения с прежней аналитикой и статус приёмки. Не записывай секреты и строки CRM. Если приёмка заблокирована, сохрани воспроизводимый кандидат отдельно от рабочего пути и перечисли оставшиеся проверки.
```
