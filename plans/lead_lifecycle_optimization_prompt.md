# Промпт для агента по оптимизации `lead_lifecycle.rq`

```text
Работай в проекте crm_pulse_monitor. Прочитай plans/lead_lifecycle_optimization.md и выполни план. Цель — измеримо ускорить queries/lead_lifecycle.rq и /api/lead-pulse, сохранив показатели страницы «Лиды» и контракт одноимённого MCP-запроса.

1. Проверь инструкции проекта и состояние рабочего дерева. Сохрани изменения пользователя. Изучи queries/lead_lifecycle.rq, lead_pulse() и get_lead_pulse() в server.py, static/leads.js, регистрацию запроса в mcp/mcp_queries.py и профайлер mcp/profile_graphdb.py. Используй logs/graphdb-benchmark-4.json как исторический ориентир. Для сравнения сними свежую базу.

2. Подтверди, что тестовые MCP и дашборд подключены к GraphDB bitrix24_v2_parallel_2 с одним префиксом именованных графов. Используй читающие SPARQL-запросы и один снимок данных или интервал без обновлений. По возможности запусти изолированные процессы с отдельным журналом. Если данные изменились в ходе серии, повтори сравнение в сопоставимых условиях. В отчёт включай технические метаданные без секретов и строк CRM.

3. Зафиксируй исходную выборку с учётом полей, типов, несвязанных переменных и кратности строк. Сними план через onto:explain и профиль через onto:measure, если они доступны. Измеряй обычную задержку отдельным запуском, без профилирования плана.

4. Реализуй варианты B, C и D из плана отдельно от рабочего шаблона и проведи по 5–10 замеров на вариант. Для B используй максимум один маркер наличия сделки на лид. Сохрани смысл флага для любой связанной сделки и минимум даты только для сделок со stageSemantic "P". Для C изолируй каждый справочник и проверь пропущенные и многозначные ключи. Для D проверь вклад сортировки и действующий порядок выдачи. Если профиль показывает дорогой MIN, проверь ограничение лидов внутри подзапросов. Затем собери кандидат из изменений, показавших выигрыш.

5. Проверь совпадение результатов при фиксированном UTC-времени. Сравни все поля summary, 90 точек response_trend и топ‑10 red_leads с порядком элементов. Проверь контрольные случаи из плана и штатный вызов именованного MCP-запроса. Для тренда реакции нужны лиды за 119 дней, а историческая конверсия и «красные» лиды используют всю историю. Если обнаружишь дефект, исправление которого меняет KPI или список, приложи воспроизводимый пример, вынеси изменение для отдельного согласования и продолжай проверять эквивалентные варианты.

6. Выполни финальный A/B-прогон. Пример запуска из каталога проекта:

python -m mcp.profile_graphdb --url http://127.0.0.1:8091/mcp --mcp-log logs/mcp-profile.jsonl --template lead_lifecycle --warmup 3 --repeats 50 --pause 0.5 --timeout 90 --seed 42 --output logs/lead-lifecycle-baseline.json

Подставь адрес тестового MCP и путь к активному журналу. Используй новый файл для каждого прогона. Сравни медиану и p95 по graphdb_ms, максимум, число вызовов дольше 1 с, ошибки, количество строк и размер ответа. Проверь полноту graphdb_ms и отдельно замерь /api/lead-pulse при промахе кэша.

7. Критерий приёмки — медиана и p95 минимум вдвое ниже свежего исходного прогона, 50/50 успешных вызовов и совпадение результатов с учётом отдельно согласованных исправлений. При выполнении критериев внеси выбранную правку в рабочий запрос, проверь штатные вызовы через MCP и API и повтори полный бенчмарк 12 шаблонов без --template. Если ни один вариант не прошёл приёмку, сохрани результаты и покажи, где остаётся задержка по доступным замерам.

8. Сохрани JSON прогонов и итоговый отчёт рядом с исходным бенчмарком. Укажи изменённые файлы, репозиторий, условия и команды запуска, сравнение вариантов и результаты проверок. Если GraphDB или журнал недоступны, выполни доступные локальные проверки, укажи конкретный блокер и команды для недостающих замеров. Подтверждай ускорение только сопоставимыми измерениями GraphDB.
```
