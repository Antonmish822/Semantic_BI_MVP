# План: управление онтологиями через CRM Pulse Monitor

## Цель и границы

Сделать страницу `/ontologies`, на которой администратор может просмотреть существующие TTL-файлы, создать онтологию из загруженного `.ttl`, отредактировать текст, проверить его, сохранить и отдельно опубликовать в RDF-хранилище. Содержимое `ontologies/*.ttl` — источник истины. Именованные графы хранилища — опубликованные копии файлов. CRM-данные и действующие страницы показателей сохраняют текущий режим чтения.

Первая версия поддерживает запись в GraphDB. При `RDF_BACKEND=fuseki` страница может показывать файлы, но публикация должна явно сообщать о неподдерживаемом backend (`501`). Удаление файлов и графов в первую версию не входит.

## Текущее состояние

- `server.py` обслуживает страницы и JSON API через `ThreadingHTTPServer`; API управления реализовано без нового веб-фреймворка.
- `RDFStoreClient` выполняет только SPARQL SELECT. Адрес GraphDB repository и учётные данные берутся из `.env`.
- Четыре онтологии лежат в `ontologies/`; соглашение об URI описано в `ontologies/README.md`.
- Dockerfile не копирует `ontologies/`. Compose использует `read_only: true` и запускает процесс от UID 10001.
- В проекте нет зависимости для разбора Turtle. Добавить `rdflib` в `pyproject.toml` и образ.

## Инварианты

1. Только файл определяет аксиомы. API публикации всегда читает актуальный файл с диска; текст запроса от браузера не отправляется в RDF напрямую.
2. Для файла `<slug>.ttl` URI графа равен `urn:bitrix24:ontology:<slug>`. В TTL должен быть ровно один субъект с `rdf:type owl:Ontology`, равный этому URI. Slug: строчные латинские буквы, цифры и дефисы, без начального/конечного дефиса; допускаются только файлы верхнего уровня `ontologies/`.
3. Сохранение файла и публикация — разные операции. Неудачная публикация не откатывает сохранённый файл; UI показывает состояние «изменения не опубликованы».
4. Сервер не принимает произвольный путь, URL GraphDB или URI графа от клиента.
5. Секреты GraphDB и администрирования никогда не передаются в JSON-ответах и не пишутся в логи.

## Страница и сценарий

Добавить `static/ontologies.html` и `static/ontologies.js`, ссылку «Онтологии» в навигацию всех страниц и обработку `/ontologies` в `server.py`.

На странице показать список файлов, класс/описание из TTL, URI графа, время изменения файла и состояние: «совпадает с графом», «есть неопубликованные изменения», «граф отсутствует», «база недоступна». При выборе файла показать редактор Turtle, кнопки «Проверить», «Сохранить», «Опубликовать» и результат каждого действия. Создание нового файла — через выбор локального `.ttl` или ввод slug с пустым шаблоном; обе формы проходят те же проверки. При уходе со страницы с несохранённым текстом предупредить пользователя.

Для отображения состояния сравнивать RDF-графы как наборы триплетов, а не побайтово: Turtle и ответ GraphDB могут отличаться порядком и идентификаторами blank nodes. `rdflib.compare.isomorphic` подходит для небольших графов онтологий. Состояние выбранной онтологии определяется по запросу чтением её именованного графа и RDF-изоморфным сравнением; список не инициирует сетевые запросы по всем графам. Статус из GraphDB не изменяет файл.

## API

| Маршрут | Назначение |
|---|---|
| `GET /api/ontologies` | Список допустимых TTL-файлов и локальных метаданных. |
| `GET /api/ontologies/{slug}` | Текст TTL, URI графа, SHA-256 текущего файла, состояние публикации. |
| `POST /api/ontologies/validate` | Синтаксис Turtle, размер и соответствие `owl:Ontology` ожидаемому URI; ничего не сохраняет. |
| `POST /api/ontologies` | Создать новый файл после проверки; вернуть 409, если он уже есть. |
| `PUT /api/ontologies/{slug}` | Проверить и атомарно сохранить файл; запрос содержит предыдущий SHA-256. |
| `POST /api/ontologies/{slug}/publish` | Прочитать файл и заменить только соответствующий именованный граф GraphDB. |

Все ответы — JSON с понятным кодом ошибки. Ограничить тело запроса (например, 256 КиБ). Для PUT сравнить SHA-256 на диске с `expected_sha256` внутри блокировки; при несовпадении вернуть 409 с новым хешем. После успешной проверки писать во временный файл в каталоге `ontologies/`, сбрасывать его на диск и выполнять `os.replace` под блокировкой. Историю версий обеспечивает система контроля версий; временные файлы не включаются в список онтологий.

## Проверка и публикация

Для проверки использовать `rdflib.Graph.parse(data=..., format="turtle")`. Проверить единственность `owl:Ontology`, его URI, размер, непустой набор триплетов и отсутствие синтаксических ошибок. Проверка синтаксиса не доказывает, что reasoner поддерживает произвольную OWL-аксиому; сообщать об этом в UI без блокировки сохранения.

Для GraphDB добавить в клиент методы чтения и замены графа через Graph Store Protocol: `/repositories/<repository>/rdf-graphs/service?graph=<encoded URI>`. Публиковать `PUT` с `Content-Type: text/turtle`, затем `GET` этого же графа и сравнивать RDF-изоморфность с файлом. При HTTP/сетевой ошибке показать её без раскрытия учётных данных. Не повторять PUT вслепую после таймаута: сначала прочитать граф и определить, применилось ли изменение. Если GraphDB отклоняет Turtle, сохранённый файл остаётся источником истины и получает статус ошибки публикации.

Опциональная проверка вывода типа для четырёх классификаторов выполняется отдельным read-only SPARQL-запросом. Нулевой результат не считать ошибкой публикации: в базе может не быть соответствующих данных.

## Доступ и развёртывание

- Административные API закрыть отдельным секретом `ONTOLOGY_ADMIN_TOKEN`, который обязателен для включения записи. Сравнивать через `hmac.compare_digest`; не хранить токен в `localStorage`. Проверять Origin для изменяющих запросов, не включать CORS. Ограничение публикации на `127.0.0.1` из Compose сохранить.
- Добавить `./ontologies:/app/ontologies:rw` в Compose. Корневую файловую систему контейнера оставить read-only. Обеспечить UID 10001 право записи в каталог на хосте; описать настройку прав в README. Для сборки без тома также копировать `ontologies/` в образ для чтения.
- В локальном запуске страница работает с тем же каталогом `ontologies/`. Если секрет не задан или каталог недоступен на запись, API чтения работает, а операции изменения возвращают явную ошибку конфигурации.
- Обновить `crm_pulse_monitor/README.md` и `ontologies/README.md`: сценарий редактирования, публикация, переменные окружения, Docker-монтирование и правило URI. Уточнить прежнюю формулировку «read-only»: показатели читают данные, а административная страница изменяет только файлы онтологий и их именованные графы.

## Порядок реализации и критерии готовности

1. Вынести работу с файлами и RDF-графами в отдельный модуль, добавить парсер и конфигурацию. Реализовать безопасное перечисление и проверку TTL.
2. Реализовать API чтения, проверки, создания и атомарного сохранения с защитой от конкурирующих изменений.
3. Реализовать публикацию в GraphDB и сравнение загруженного графа с файлом; корректно обработать таймаут и недоступность базы.
4. Добавить страницу, навигацию, отображение состояния и сообщения об ошибках.
5. Настроить Docker/Compose, доступ администратора и документацию.
6. Проверить значимые сценарии: валидный/невалидный TTL, неправильный URI онтологии, обход пути, конфликт SHA-256, сохранение без публикации, успешная публикация, ошибка GraphDB, сохранность существующих графов и работа трёх прежних страниц. Для интеграционной проверки использовать отдельный временный граф, не менять действующие четыре графа без явной задачи на публикацию.

Реализовано: администратор может изменить TTL в браузере, увидеть сохранённый файл, отдельно опубликовать его в вычисленный граф и получить подтверждение равенства RDF-содержимого файла и графа. Каталог подключён постоянным томом. Локальные автоматические тесты добавлены, но требуют установленной зависимости `rdflib`.
