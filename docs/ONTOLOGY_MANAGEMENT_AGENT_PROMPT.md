# Промпт для ИИ-агента

Реализуй в проекте `crm_pulse_monitor` административную страницу управления TTL-онтологиями. Прочитай `docs/ONTOLOGY_MANAGEMENT_PLAN.md`, `ontologies/README.md`, `server.py`, `Dockerfile`, `compose.yaml` и существующие страницы. Выполни задачу до рабочего результата, обнови документацию и сообщи об изменённых файлах и результатах проверки.

## Требуемое поведение

1. Страница `/ontologies` показывает файлы из `ontologies/*.ttl`, позволяет открыть и отредактировать Turtle, проверить его, сохранить файл, создать новый файл из текста/локального `.ttl` и отдельно опубликовать сохранённую версию в GraphDB. Добавь ссылку на страницу в навигацию всех страниц.
2. Файл — единственный источник аксиом. Никогда не публикуй в RDF текст, который не был успешно сохранён на диск. Сохранение файла не должно автоматически менять RDF-граф.
3. Вычисляй URI графа из slug файла: `foo-classification.ttl` → `urn:bitrix24:ontology:foo-classification`. Проверяй, что в TTL ровно один субъект `a owl:Ontology` с этим URI. Не принимай путь или URI графа от клиента. Сохрани существующие четыре онтологии и их URI.
4. Перед сохранением проверяй размер, синтаксис Turtle и URI онтологии. Используй `rdflib`; добавь зависимость в `pyproject.toml` и Dockerfile. Для существующего файла требуй `expected_sha256`; при конкурирующем изменении отвечай 409. Записывай новый текст атомарно через временный файл и `os.replace` под блокировкой. Не допускай обхода `ontologies/` через имя файла.
5. Для публикации добавь в серверный клиент GraphDB Graph Store Protocol `PUT` по `/repositories/<repo>/rdf-graphs/service?graph=<IRI>`. Используй текущие переменные подключения и серверную авторизацию к GraphDB. После PUT прочитай граф и сравни его с файлом как RDF-граф, учитывая blank nodes. Обрабатывай сетевые ошибки и таймауты без слепого повторения PUT. При `RDF_BACKEND=fuseki` верни понятный 501 для публикации.
6. Добавь API чтения списка и файла, проверки текста, создания, сохранения и публикации. Ошибки возвращай JSON с подходящими HTTP-кодами. Административные операции защищай `ONTOLOGY_ADMIN_TOKEN` из окружения, проверкой Origin и ограничением размера запроса. Токен не логируй и не записывай в постоянное браузерное хранилище. При отсутствии токена или прав на запись не разрешай изменение файлов и графов.
7. В Compose подключи `./ontologies` как постоянный том с записью, сохрани `read_only: true` для корневой файловой системы. Учти, что процесс работает под UID 10001. Обнови `.env.example`, основной README и `ontologies/README.md` с настройками, порядком действий и различием между сохранением и публикацией.

## Рабочие правила

- Сохрани действующие маршруты и поведение страниц показателей; не открывай доступ к произвольным SPARQL Update, путям файловой системы и графам.
- Не заменяй и не удаляй действующие именованные графы при разработке или проверке. Для интеграционных проверок используй отдельный временный граф с явным именем и убери его после проверки.
- Реализуй решение в стиле существующего проекта: Python-сервер и статические HTML/CSS/JS, без нового веб-фреймворка.
- Добавь только проверки, которые подтверждают важные риски: синтаксис и URI TTL, безопасность пути, конфликт редакций, атомарность сохранения, адрес целевого графа, неуспешная публикация и сохранность прежних страниц. Не создавай тесты, дублирующие реализацию.
- Если выяснится, что деталь плана несовместима с текущим GraphDB API или способом запуска проекта, выбери рабочий вариант, объясни отличие и обнови план/README.

## Критерий завершения

После локального запуска администратор открывает `/ontologies`, изменяет и сохраняет TTL, видит статус «не опубликовано», публикует файл в вычисленный именованный граф и видит подтверждённое совпадение RDF-содержимого. Сохранённый файл переживает перезапуск Docker-контейнера. Неадминистратор не может изменить файл или граф.
