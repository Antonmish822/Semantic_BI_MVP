# План реализации ИИ-помощника по онтологиям

## 1. Цель и готовый сценарий

Администратор открывает `/ontologies`, выбирает TTL-файл либо задаёт slug нового, затем описывает желаемые аксиомы обычным текстом. Помощник собирает актуальные сведения о признаках, файлах и опубликованных графах, при необходимости делает ограниченные read-only SPARQL-запросы и возвращает объяснение, источники, оценку влияния и предлагаемый TTL. Администратор просматривает diff и переносит предложение в редактор. Действующие кнопки «Проверить», «Сохранить» и «Опубликовать» завершают работу.

Помощник не получает инструментов записи в файлы или GraphDB. Источник истины — `ontologies/*.ttl`. Он не заменяет существующий путь сохранения и публикации.

## 2. Исходные компоненты проекта

- `server.py`: `ThreadingHTTPServer`, серверные RDF-настройки, маршруты `/api/ontologies` и проверка `ONTOLOGY_ADMIN_TOKEN`/Origin для POST и PUT.
- `ontology_admin.py`: проверка slug, `parse_ttl`, SHA-256, атомарное сохранение, чтение/публикация именованных графов, RDF-изоморфное сравнение.
- `static/ontologies.html` и `static/ontologies.js`: список, редактор, проверка, сохранение и публикация. Административный токен находится в памяти страницы.
- `docs/entity_properties.csv`: инвентарь предикатов по семи типам; строка означает, что предикат обнаружен, но не отражает полноту заполнения.
- `ontologies/*.ttl` и графы `urn:bitrix24:ontology:*`: соответственно файловая и опубликованная версии правил.

Сначала прочитать `docs/ONTOLOGY_ASSISTANT_CONCEPT.md` и сохранить эти границы при реализации.

## 3. Провайдер и конфигурация

Использовать официальный Python пакет `openai` с `base_url=https://polza.ai/api/v1` и Chat Completions API Polza.ai. Начальная модель — `openai/gpt-6-luna`. Передавать `model` явно в каждом запросе; не фиксировать модель в коде. Добавить в `.env.example` и README:

```dotenv
POLZA_API_KEY=
ONTOLOGY_AI_BASE_URL=https://polza.ai/api/v1
ONTOLOGY_AI_MODEL=openai/gpt-6-luna
ONTOLOGY_AI_TIMEOUT=60
ONTOLOGY_AI_MAX_TOOL_CALLS=4
```

Добавить пакет `openai` в `pyproject.toml` и Dockerfile с согласованными ограничениями версий. Ключ не попадает в HTML, JS, JSON-ответы и логи. При пустом ключе API помощника возвращает 503, а редактор онтологий работает как раньше. В интерфейсе показывать имя активной модели, полученное из серверной конфигурации. В первой версии смена модели происходит через параметр окружения и перезапуск сервера; браузер не передаёт произвольное имя модели.

Ограничить общий таймаут, размер ответа, количество вызовов функций и число шагов диалога. Для первого выпуска использовать обычный JSON-ответ; потоковую выдачу добавить позднее при необходимости.

## 4. Сбор контекста: детерминированные инструменты чтения

Реализовать отдельный `ontology_assistant.py`, не смешивая работу модели с `ontology_admin.py`. Инструменты принимают типизированные аргументы, проверяют допустимые значения и возвращают короткий JSON с происхождением данных.

| Инструмент | Вход | Результат и ограничение |
|---|---|---|
| `list_entity_properties` | тип из CSV | Предикаты этого типа и другие типы, в которых они встречаются. |
| `read_ontology_file` | допустимый slug | TTL, SHA-256, URI; максимум 256 КиБ. |
| `list_ontology_graphs` | без аргументов | URI графов только с префиксом `urn:bitrix24:ontology:`. |
| `read_ontology_graph` | URI из списка/вычисленный из slug | RDF опубликованного графа и статус совпадения с файлом. |
| `property_profile` | предикат из CSV, тип сущности | Число субъектов, наличие в других типах и доля субъектов типа с предикатом; только агрегаты. |
| `classification_profile` | класс из разрешённого словаря | Число ресурсов класса и пересечения с другими классами. |

Список разрешённых типов и предикатов строить из CSV при чтении; `GRAPH_PREFIX` и шаблон `:<type>:` использовать так же, как существующие SPARQL-запросы дашборда. Извлечение фактических данных делать шаблонными `SELECT`/`ASK` запросами с фиксированными графовыми областями, лимитами и таймаутом `RDF_TIMEOUT`. Модель не может передать сырой SPARQL, произвольный URL или путь к файлу. В запросы модели по умолчанию передавать агрегаты, имена полей и URI графов, без CRM-литералов с персональными данными.

При старте запроса передать модели текущий текст редактора (включая несохранённые изменения), его SHA-256 и SHA-256 файла, если файл существует. Два источника называть отдельно: «редактор» и «сохранённый файл». При чтении GraphDB также указывать URI графа, время и результат сравнения с файлом. Ответы инструментов маркировать как данные, не как инструкции.

## 5. Оркестрация модели

Один агент выполняет короткий цикл Chat Completions с function calling: отправляет задачу и доступные read-only функции, исполняет не более `ONTOLOGY_AI_MAX_TOOL_CALLS` выбранных вызовов, возвращает результаты модели и получает окончательный ответ. Для первых четырёх онтологий можно заранее вложить компактную сводку CSV/файла, чтобы уменьшить число вызовов. Вызовы функций проверять на сервере независимо от JSON Schema, присланной провайдеру.

Системная инструкция задаёт роль: предлагать аксиомы для текущего TTL, применять соглашение об URI, различать факты и предположения, не обещать вывод при одном лишь синтаксическом разборе, предупреждать о широкой семантике `rdfs:domain`/`rdfs:range` и не трактовать `owl:hasKey` как правило классификации. Инструкции из TTL, CSV и RDF-литералов не выполняются. История диалога ограничивается по размеру; каждый новый запрос перечитывает актуальную версию файла и статусы графов.

Финальный ответ модели запрашивать в структурированной форме. Минимальный контракт:

```json
{
  "summary": "Что и зачем меняется",
  "proposed_ttl": "Полный Turtle для текущего slug",
  "evidence": [{"source": "csv|file|graph|sparql", "reference": "...", "finding": "..."}],
  "impact": {"estimated_subjects": 0, "possible_cross_type_matches": [], "limits": "..."},
  "warnings": [],
  "assumptions": []
}
```

При отсутствии достаточных данных допустим ответ без `proposed_ttl` с конкретным вопросом и собранными фактами. Не полагаться только на JSON-валидность ответа провайдера: разобрать схему локально и отдельно проверить Turtle через `parse_ttl`. Привязать ответ к `slug`, SHA-256 редактора и SHA-256 сохранённого файла, на которых он основан. Diff вычислять на сервере (`difflib`) из присланного текста редактора и проверенного предложения, а не доверять diff модели.

## 6. Проверка смысла и оценка влияния

Минимальные проверки предложения:

1. `proposed_ttl` проходит `parse_ttl`, размер не превышает `MAX_TTL_BYTES`, единственный `owl:Ontology` соответствует slug.
2. Предикаты, для которых предлагается `rdfs:domain` или `rdfs:range`, сопоставлены с CSV и фактическим `property_profile`. Совпадение предиката с несколькими типами помечается предупреждением; вывод по `rdfs:domain` означает «любой субъект этого свойства».
3. Предложенные `owl:hasKey`, `owl:disjointWith`, `owl:intersectionOf`, `owl:someValuesFrom` показываются с объяснением их последствий и известных ограничений текущего reasoner. Синтаксически корректный TTL не считать доказательством вывода.
4. Оценка числа затронутых субъектов основана на read-only SPARQL и отмечается как предварительная. Точный прогон нового reasoner правила требует отдельной staging repository; не загружать черновик в производственный repository для «предпросмотра».

Если проверка не прошла, UI получает объяснение и сырой текст ответа для обсуждения с помощником, но кнопка «Применить в редактор» заблокирована.

## 7. HTTP API

Добавить в `server.py` маршрут `POST /api/ontology-assistant/suggest`. Запрос: `slug`, `editor_text`, `file_sha256` (или `null` для нового файла), `editor_sha256`, `message`, ограниченная история диалога. Ответ: модель, summary, proposed_ttl или вопрос, diff, evidence, impact, warnings, обе версии SHA и флаг `applicable`. Ограничить тело запроса отдельным пределом, учитывающим TTL и историю (например, 384 КиБ). Административная авторизация, Origin и обработка ошибок должны совпадать с существующим `_ontology_write`, но лимиты сообщений и ошибок модели выделить отдельно.

Можно добавить `GET /api/ontology-assistant/config` с `enabled`, `model` и разрешёнными действиями без ключа. API не принимает `model` и `base_url` от браузера. Ошибки Polza.ai классифицировать как недоступность, таймаут, лимит и некорректный ответ; не возвращать клиенту заголовки авторизации или полный upstream payload. Логировать длительность, число вызовов инструментов и тип ошибки, но не ключ, CRM-данные или полный промпт.

## 8. UI и применение предложения

Расширить `static/ontologies.html`, `static/ontologies.js` и стили: на широком экране редактор и панель помощника рядом, на узком панель ниже/вкладкой. Сохранять видимость текущего файла, целевого URI графа и статуса публикации. В панели дать поле запроса, быстрые задачи («Создать аксиому», «Проверить правило», «Почему нет вывода?», «Оценить влияние»), список источников, предупреждения, diff и кнопки «Применить в редактор»/«Попросить исправить».

При ответе агента сравнить присланный `editor_sha256` с текущим текстом textarea и `file_sha256` с текущей выбранной версией. Если редактор или файл изменился, не применять старое предложение и показать действие «Пересчитать по текущему тексту». После применения пометить редактор как изменённый; дальше использовать действующие «Проверить» → «Сохранить» → «Опубликовать». Для нового slug помощник предлагает полный шаблон и переносит его в сценарий создания. Токен администратора остаётся в памяти страницы.

## 9. Файлы и развёртывание

Ожидаемые изменения: новый `ontology_assistant.py` и шаблоны SPARQL в `queries/`; маршруты в `server.py`; панель в `static/ontologies.html`, `static/ontologies.js`, `static/styles.css`; зависимости в `pyproject.toml`/Dockerfile; параметры в `.env.example`; документация в `README.md` и `ontologies/README.md` при необходимости. Существующий `compose.yaml` уже монтирует папку онтологий; добавить только переменные окружения/секреты, требуемые новым API. Сервису нужен исходящий HTTPS-доступ к `polza.ai`.

## 10. Этапы работ и проверки

1. **Контекст без LLM.** Реализовать CSV-каталог, чтение файлов/графов и два агрегирующих SPARQL-инструмента. Проверить, что общий предикат вроде `categoryCode` не считается уникальным для сделки.
2. **Вызов Polza.ai.** Добавить конфигурацию, Chat Completions, ограниченный цикл функций и обработку ошибок. Проверить запрос с моделью `openai/gpt-6-luna` без передачи секретов клиенту.
3. **Проверка ответа.** Структурированный контракт, разбор TTL, серверный diff, привязка к версиям, предупреждения о семантических пересечениях.
4. **Интерфейс.** Чат, карточки источников, diff, применение в редактор и работа с новым slug. Сохранение и публикация остаются на существующих кнопках.
5. **Документация и приёмка.** Описать настройку Polza.ai, модель, ограничения данных, пример диалога и порядок действий администратора.

Достаточно проверить следующие существенные сценарии: действующий файл с несохранёнными изменениями; новый файл; неверный Turtle; неверный URI; общий предикат у двух типов; устаревшие SHA; ошибка/таймаут Polza.ai; недоступная GraphDB; отсутствие ключа; неизменность TTL и именованных графов после любого вызова помощника; работоспособность существующих страниц и API. Подменять Polza.ai и GraphDB в автоматических проверках, а реальный интеграционный запрос выполнять только с настроенным ключом.

## 11. Критерии завершения

- Администратор может описать желаемые аксиомы промптом для выбранного или нового TTL и получить применимое предложение с проверенным Turtle, diff и происхождением фактов.
- Модель задаётся `ONTOLOGY_AI_MODEL` и по умолчанию равна `openai/gpt-6-luna`; фактическое значение видно в UI.
- Модель и её инструменты не записывают файлы и графы. Применение предложения меняет только textarea; сохранение и публикация происходят через действующий механизм.
- Ошибки провайдера, конфликты версий и неоднозначные свойства не приводят к тихой потере текста или неверной публикации.

Документация Polza.ai: [быстрый старт](https://polza.ai/docs/glavnoe/quickstart), [tool calling](https://polza.ai/docs/gaidy/tool-calling), [карточка GPT-6 Luna](https://polza.ai/models/openai/gpt-6-luna).

## Реализация в проекте

Реализованы `ontology_assistant.py`, API `GET /api/ontology-assistant/config`, `GET /api/ontology-assistant/version` и `POST /api/ontology-assistant/suggest`, панель помощника справа от редактора на широком экране и ниже на узком. Доступ к suggest проверяет тот же `ONTOLOGY_ADMIN_TOKEN` и `Origin`, а ключ провайдера хранится только на сервере.

Каталог признаков переименован в `docs/entity_properties.csv`: BuildKit в текущем окружении падал при передаче кириллического имени файла в build context (`followpaths`). ASCII-имя позволило штатно собрать образ из Compose. Добавлен `.dockerignore`, исключающий `.env`, Git-метаданные, тесты и Markdown-документацию из контекста.

После эксплуатации добавлена UTF-8-safe передача admin token: браузер использует `Bearer-UTF8` с Base64URL, сервер также принимает прежний ASCII `Bearer`. Прямые просьбы создать онтологию теперь должны возвращать условный TTL с допущениями/предупреждениями даже при неустановленном типе значений, а уточняющий вопрос может сопровождать предложение вместо блокирования генерации.

Инструменты исполняют только фиксированные SELECT и чтение разрешённых TTL/Graph Store URI. SPARQL параметры ограничены CSV, типами и словарём классов. Инструментальные данные содержат агрегаты и аксиомы, но не возвращают CRM-литералы или URI экземпляров. Количество вызовов инструментов, число проверяемых профилей, общий таймаут и размеры запроса/ответов ограничены.

Сначала выполняются вызовы чтения через Chat Completions с `tools`; финальный запрос отдельно использует `response_format=json_schema`. Если провайдер вернёт HTTP 400 на JSON Schema, выполняется один запрос с инструкцией JSON и локальной строгой проверкой контракта. Такой запасной путь отражает OpenAI-compatible поверхность Polza.ai при возможных различиях поддержки формата у моделей. В обоих режимах результат проходит локальную проверку структуры и `parse_ttl`.

Применение предложения сверяет SHA редактора и повторно запрашивает версию файла, чтобы блокировать устаревший ответ. Предварительная оценка одного `rdfs:domain` вычисляется по профильному read-only запросу; для нескольких доменов количество не суммируется без анализа пересечений. Предложение никогда не вызывает запись файла или GraphDB.

Проверки выполняются на подменённых Polza.ai/GraphDB. Интеграционный вызов не выполнялся: в локальном `.env` ключ Polza.ai не настроен. Изменения четырёх исходных TTL и опубликованных графов не требуются.
