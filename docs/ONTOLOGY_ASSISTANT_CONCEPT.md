# Концепция ИИ-помощника для онтологий

## Назначение

Добавить на страницу `/ontologies` помощника администратора, который по описанию задачи предлагает новые OWL 2 RL-аксиомы, объясняет существующие правила и помогает исправлять ошибки классификации. Помощник подготавливает **предложение к редактированию TTL**. Сохранение файла и публикация в RDF остаются явными действиями администратора через существующий интерфейс.

Примеры задач: «Классифицируй стадии», «Почему не выводится `b24:Activity`?», «Проверь, не отнесёт ли `rdfs:domain b24:User` другие сущности к сотрудникам», «Предложи минимальную правку этой онтологии».

## Контекст, доступный помощнику

| Источник | Что брать | Зачем |
|---|---|---|
| `docs/entity_properties.csv` | Тип сущности и список предикатов | Найти признаки-кандидаты и общие свойства. CSV показывает наличие признака в типе, но не долю его заполнения. |
| `ontologies/*.ttl` | Текст, SHA-256, URI онтологии | Учитывать каноническую файловую версию и соседние правила. |
| Именованные графы `urn:bitrix24:ontology:*` | Опубликованные аксиомы и их отличие от файлов | Диагностировать расхождение между файлом и GraphDB. |
| RDF-данные CRM | Только агрегаты и ограниченные выборки по заранее определённым SELECT/ASK-запросам | Проверить распространённость признака, пересечение типов, число уже классифицированных ресурсов. |
| Результаты действующего API | Ошибки проверки TTL, статус публикации, версия файла | Предлагать исправления к актуальному состоянию редактора. |
| `ontologies/README.md` и локальные модели | Соглашение об URI и применяемые паттерны OWL 2 RL | Не предлагать несовместимые URI или неподдержанные правила. |

Для каждой справки показывать происхождение: имя файла и SHA, URI графа, время чтения базы и текст/идентификатор аналитического запроса. Данные из CSV и RDF могут расходиться; помощник должен явно отмечать это. Значения клиентских полей и персональные данные не отправлять модели по умолчанию: для выбора правила достаточны имена предикатов и агрегаты.

## Устройство на сервере

Новый модуль `ontology_assistant.py` собирает контекст и обращается к Polza.ai через OpenAI-совместимый Python SDK. Ключ и модель задаются на сервере; браузер не видит ключ. Если ключ не задан, страница редактора продолжает работать, а панель помощника показывает причину недоступности.

### Параметры модели и API

```dotenv
POLZA_API_KEY=...
ONTOLOGY_AI_BASE_URL=https://polza.ai/api/v1
ONTOLOGY_AI_MODEL=openai/gpt-6-luna
ONTOLOGY_AI_TIMEOUT=60
```

Начальная модель — `openai/gpt-6-luna`; её идентификатор не зашивается в код и может быть заменён через `ONTOLOGY_AI_MODEL`. Поле `model` передаётся в каждом запросе к Polza.ai. В панели администратора показывать фактически выбранную модель. API-ключ хранится только в `.env`/секретах окружения и не возвращается клиенту.

Для первой реализации использовать OpenAI-совместимый Chat Completions API Polza.ai с function calling: он описан в документации сервиса и поддерживается выбранной моделью. Сервер исполняет вызванные функции чтения и возвращает их результаты модели. Предложение TTL принимать в структурированном формате и дополнительно проверять локально. Polza.ai также предоставляет Responses API; переход на него возможен без изменения инструментов сбора RDF-контекста, если понадобится его функциональность.

Сервер предоставляет модели ограниченный набор инструментов чтения:

1. `list_properties(entity_type)` — сведения CSV и актуальная статистика по предикатам.
2. `read_ontology(slug)` — текст файла, версия и опубликованное состояние.
3. `list_ontology_graphs()` / `read_ontology_graph(uri)` — только графы из разрешённого namespace.
4. `property_profile(predicate)` — число субъектов, распределение по типам сущностей и доля заполнения по шаблонным SPARQL-запросам.
5. `classification_profile(class_uri)` — число ресурсов класса и возможные пересечения с другими классами.

Инструменты выполняются сервером, а не произвольным SPARQL, сгенерированным моделью. Все запросы — только SELECT/ASK, с лимитами, таймаутом и проверкой URI. Инструкции, попавшие в RDF-литералы или текст TTL, считаются данными и не могут менять права помощника.

Один запрос к помощнику получает выбранный файл, **текущий текст редактора** и его базовый SHA-256. Поэтому он видит ещё не сохранённые изменения, но читает опубликованный граф отдельно. При длинном диалоге сервер передаёт компактную историю и обновляет факты из файлов/базы перед очередным предложением. Ответ модели должен быть структурированным: цель, краткое объяснение, полный предлагаемый TTL или точечный diff, использованные факты, предположения и вопросы, если данных не хватает.

## Проверка предложения

Сервер проверяет ответ до показа кнопки «Применить»: синтаксис Turtle, единственный `owl:Ontology`, соответствие URI имени файла, отсутствие неконтролируемых внешних импортов и ожидаемого класса. Уже существующая `parse_ttl` из `ontology_admin.py` подходит для базовой проверки. Для OWL 2 RL добавить перечень применяемых конструкций и предупреждать о тех, которые GraphDB в этом repository не выводит ожидаемым образом. Известный пример: правило для активности с `owl:intersectionOf` и двумя `owl:someValuesFrom` не дало вывод; вариант с `rdfs:domain` дал.

Перед рекомендацией `rdfs:domain` проверять, встречается ли предикат у других типов: этот вывод сработает по **каждому** использованию свойства. Для `rdfs:range` проверять, что объект действительно URI нужного класса. При предложении `owl:hasKey` объяснять, что ключ отвечает за отождествление известных экземпляров и не классифицирует их.

«Оценка влияния» в первой версии — read-only расчёт числа субъектов с выбранными свойствами, возможных пересечений классов и примеров URI. Он даёт прогноз, а не результат полного OWL 2 RL вывода. Для точной проверки будущих изменений нужна отдельная staging repository: загрузка пробной онтологии в производственный repository меняет глобальный вывод даже при временном графе.

## UI администратора

Расширить `static/ontologies.html` и `static/ontologies.js`: рядом с редактором открыть панель «ИИ-помощник».

- Вверху панели: активный файл, статус «файл / граф совпадают или расходятся», время обновления контекста.
- Быстрые действия: «Создать правило», «Проверить текущую онтологию», «Найти причину отсутствия вывода», «Оценить влияние». Ниже — поле свободного запроса и история диалога.
- Ответ делить на объяснение, карточки доказательств (CSV, файл, граф, статистика) и вкладку diff. Для каждого изменяемого `rdfs:domain` показывать число затронутых субъектов и предупреждение о пересечении типов.
- Кнопка «Применить в редактор» переносит предложение только в текстовое поле. Появляется признак несохранённых изменений. Действующие кнопки «Проверить», «Сохранить», «Опубликовать» выполняют следующие шаги.
- Если файл изменился после подготовки ответа, показывать конфликт SHA и предлагать пересчитать предложение по новой версии.

Для нового файла панель может предложить slug и стартовый TTL, затем перенести их в существующий сценарий создания. Помощник не вызывает операции сохранения и публикации от имени администратора.

## API и доступ

Предлагаемые endpoints: `POST /api/ontology-assistant/context` для сводки доступных фактов и `POST /api/ontology-assistant/suggest` для запроса с текстом редактора, slug и базовым SHA. Сначала достаточно обычного JSON-ответа; потоковую выдачу можно добавить, если ответы станут длинными. Проверка предложенного TTL выполняется сервером до возврата. Лимитировать размер запроса и объём контекста; предусмотреть отмену долгого вызова.

Использовать существующую административную авторизацию `ONTOLOGY_ADMIN_TOKEN`; доступ к фактам о схеме и помощь в изменении онтологий относятся к той же роли. Отдельно задать лимит обращений к модели. В журнал писать идентификаторы операций, длительность и ошибки без секретов, персональных данных и полных промптов.

## Порядок внедрения

1. Сделать детерминированный сбор контекста: CSV, файлы, графы и безопасные агрегирующие SPARQL-запросы. Проверить его ответы без LLM.
2. Добавить адаптер модели, структурированный формат ответа и серверную проверку предложений.
3. Добавить панель, карточки доказательств и перенос diff в редактор.
4. Проверить сценарии на существующих онтологиях: предложение общего свойства не должно проходить без предупреждения; устаревший SHA блокирует применение; ошибка модели не влияет на файлы и GraphDB; предложенный TTL не меняет граф до явной публикации.

Первая версия считается готовой, когда администратор получает предложение, видит его основание и влияние, применяет его в редакторе и дальше использует действующий цикл проверки, сохранения и публикации. Ни одно действие модели не изменяет файл или RDF-граф напрямую.

## Реализационные заметки

При развёртывании контейнер должен копировать CSV `docs/entity_properties.csv` вместе с `ontology_assistant.py`. Помощник отправляет внешнему провайдеру текст редактора и запрос пользователя; сохранённые/опубликованные аксиомы и RDF-агрегаты передаются только через выбранные чтением инструменты. Отказ JSON Schema с HTTP 400 допускает один запрос в обычном JSON режиме с локальной проверкой контракта. В интерфейсе текст предложения применяется только после повторной проверки обеих SHA-версий.
